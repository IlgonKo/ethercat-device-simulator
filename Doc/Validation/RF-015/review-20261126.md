## 소스 대조

경로는 Soft ESC 저장소 기준이다.

- [servo_model.py](../../../src/functional_model/cia402_drive/behaviour_model/f_kr_cmmt/servo_model.py)
  - _apply_od_commands / set_target_position: OD 목표 변화가 실행 상태 변경·정지로 이어질 수 있음.
  - process_pp: 새 시작 edge마다 pp_target_position 교체, 0x6081/6083/6084 매 주기 읽기.
  - is_in_position / update_target_reached: OD의 0x607A를 기준으로 완료 계산.
  - set_mode / process_cycle: 즉시 정지 후 요청값 0x6060을 적용·계산. 요청/적용 모드 분리 필요.
  - process_pv: 위치 한계에 따른 방향 차단 없음.
  - process_jog / _software_position_limits: 현재 OD 한계 읽기, 하한/상한 역전 자동 교환.
  - process_pv/process_jog: 목표/현재 속도 크기로 가속·감속 선택. 반전 감속→0→가속을 별도로 보장하지 않음.
  - stop_at_current_position / _decelerate_to_stop: 즉시 정지·target_reached 혼용, 감속값 주기별 조회.
  - process_homing: 시작 시 정지 조건 검증 부족, cycle count 기반 시간, 시작 비트 해제/Halt에 의한 명시 취소 부족.
- [state_machine.py](../../../src/functional_model/cia402_drive/behaviour_model/f_kr_cmmt/state_machine.py): Quick Stop Active 및 감속 후 종료 전환 없음.
- [f_kr_cmmt.py](../../../src/functional_model/cia402_drive/adapter/f_kr_cmmt.py): 모드 검증 외 위치 한계 상호 검증 필요. deactivate의 목표 보존과 재시작 방지를 회귀해야 함.
- [axis.py](../../../src/functional_model/runtime/axis.py): RF-014 active/PP edge guard 및 RF-018 Fault Reset·Host 장애 처리를 재사용. 정책상 무시는 DeviceRejectedException을 던져 Axis Fault로 바꾸면 안 됨.
- [copley.py](../../../src/functional_model/cia402_drive/adapter/copley.py): PP만 지원, Halt 비트는 FMU 경계에서 제거, 가속=감속 제약. F-KR 새 정책을 이미 만족한다고 간주하지 않으며 기존 범위 회귀/차이 명시.
- unit 메타데이터 확인: 0x216E:01=256(ro), 0x2194:01=6(ro). 0x605A 정의 없음. 0x6085는 rw/초기값0이지만 Model.entries(IPC 공개 OD)에 없음.

## Motion Server 경로와 작업 경계

Linux /home/festo/Documents/motion-server의 코드를 기준으로 검토했다. Windows checkout도 아래 핵심 분기를 보조 대조했다.

| 동작 | 확인된 경로 | RF-015 처리 |
| --- | --- | --- |
| PP | handlers/command/motion.py → control/setpoint_output.py, bit12 ACK clear/set/clear 대기 | 정상 순차 이동과 중복 요청 방어 시험 분리 |
| 일반 Stop | handlers/command/axis_state.py: PP Halt, PV 속도0, Jog 방향/속도 비트 clear | 모델 입력 의미와 감속/취소 검증 |
| Disable | Stop 처리 후 CW 0x0007 | 즉시 정지 근사·재Enable 재실행 금지 |
| Jog 종료 | 방향 clear 후 exchange 5회, 이전 모드 요청. 모드 적용 확인 대기 없음 | 실제 정지 전 요청을 무시하고 요청 지속 시 정지 후 적용되는지 검증 |
| Homing | 시작 비트 clear/set, referenced low→high 확인, 종료 시 시작 비트 clear·모드 복원 | 반복 Homing과 중단 경로 회귀 |
| Reset | bit7 pulse 후 CW 0x0006/0x0007 | 기존 Fault 규칙·위치/reference 보존 회귀 |

B8 확인은 authority_release.py의 조작권 해제 정지 대기 및 reference_clients/python/examples/pick_place/program.py의 이동 완료 대기에 존재한다. 확인한 api/validator.py와 일반 move_abs/move_rel 처리 경로에는 B8 기반 운전 중 요청 차단이 없다. 정상 순차 클라이언트가 다음 이동을 기다리는 것과 서버 API 자체 차단은 구분한다.

사용자 최종 결정: **B8 기반 요청 차단은 Motion Server에서 별도 처리. 디바이스는 방어적 무시 유지.** 서버가 새 PP ACK를 기다리는 특성 때문에 무시한 요청의 API 응답이 실패일 수 있으나, 디바이스 Fault가 발생했다는 뜻은 아니다. 서버 코드나 TD는 이번 작업에서 수정/등록하지 않았다.

## 오프라인 관찰

Linux build/fmi-venv/bin/python, PYTHONPATH=src:.에서 메모리상의 Model()과 어댑터만 생성했다. 초기 가속/감속1000·속도100, step 0.008s, CW6→7→15, referenced=True로 실행 상태를 준비한 뒤 각 입력을 적용했다. 단위는 별도 표시 없는 경우 raw 값이다. 원점 설정은 시험 준비용이며 Homing 검증이 아니다.

| 입력 | 관찰 결과 |
| --- | --- |
| PP 속도100으로 운전 중 0x6081=50 | 실제 속도100→92, 실행 목표500000 유지. 현재 코드의 즉시 영향 확인 |
| 이동 중 새 PP edge와 목표600000 | 실행 목표500000→600000, ACK=true, 속도76. 방어적 무시 미구현 |
| 이동 중 목표 OD=2000000(상한1000000 초과) | pp_active=false, 속도0, OD 목표13408로 덮어씀 |
| PV 이동 중 모드 PP 요청 | 속도8→0, Mode Display=1. 정지 전 즉시 전환 |
| 위치1000001에서 상한1000000 바깥 방향 PV | 위치1000065·속도8. 위치 한계 차단 없음 |
| 위 PV 상태에서 CW0x000B Quick Stop | OPERATION_ENABLED 유지, 속도16으로 증가 |
| SDO 하한2000000/기존상한1000000 | 쓰기 허용, 내부 유효 한계가 [1000000,2000000]으로 자동 교환 |

이 결과는 합의 정책과의 차이를 드러내는 현재 구현 관찰이며 새 합격 시험이 아니다.

## 추가 — Motion Server 신규 제한과 실제 Copley 상태 관찰

사용자 정정: Jog는 모드 전환 예외가 아니라 이미 Jog 모드인 동안 운전 명령만 예외다. 이 조건은 F-KR 합의 정책과 일치한다. move_vel(0) API 제한은 Stop 내부 PDO 속도0 쓰기를 금지하는 의미가 아니다.

실제 FMU를 CopleyAdapter로 메모리상 생성했다. 목표100000, Profile Velocity100, step8ms, CW6→7→15→0x3F, 이후0x0F 10주기, Halt0x010F 11주기, Disable0x0007을 적용했다. 네트워크·실축·컨테이너는 조작하지 않았다. 다음 값은 raw 출력이다.

| 시점 | Statusword | B8 | 위치 | 속도 |
| --- | --- | --- | --- | --- |
| PP 시작 | 0x9237 | OFF | 20 | 4 |
| 10주기 후 | 0x8237 | OFF | 1980 | 44 |
| Halt 첫 주기 | 0x8237 | OFF | 2352 | 48 |
| Halt 추가 10주기 후 | 0x8237 | OFF | 7832 | 88 |
| Disable | 0x8233 | OFF | 7832 | 0 |

Copley B8 미표시와 기존 Halt 무시를 확인했다. 기존 PP만 지원한다는 설명만으로 B8 기반 차단과 일반 PP Stop 호환성을 충족한 것으로 볼 수 없다. 새 서버 정책의 구현 자체를 시험한 것은 아니다.
