## 구현 및 저장 계약

F-KR 어댑터의 FKrUnits가 같은 공개 OD를 읽고 동작 모델 경계의 값을 변환한다. 별도 OD나 파라미터 사본은 만들지 않는다. 직선축 계산 상태/PP·정지 스냅샷은 m, m/s, m/s², s다. Controlword/Statusword/Mode는 정수·비트다. EtherCAT 원시값과 접근 권한, PDO·IPC 형식은 유지했다. 읽기 전용 단위 지수에 따른 배율은 인스턴스 생성 시 확보한다. 회전축은 기존 degree 계열 스케일을 유지하며 modulo/최단 경로 기능은 추가하지 않았다.

F-KR 저장 스키마는 **3, 23개 OD**다. 기존 21개에 0x605A(옵션 2), 0x6085(양의 감속값)를 추가했다. Copley는 스키마 1/8개를 유지한다. 구형 파일은 정상 시작 경로에서 오류로 거부하며 자동 보정하지 않는다.

기존 명시적 오프라인 이관 유틸리티를 현재 스키마까지 연결했다. 원본 체크섬·장치 정체성·목록·값 검증, 저장소 잠금, 원본 .schema1.bak/.schema2.bak 보존 후 원자적 저장을 유지한다. schema 2→3의 새 0x6085는 저장된 0x6084 값, 0x605A는 2다. schema 1은 추가로 명시적 Profile Velocity가 필요하다. 이미 schema 3이면 검증만 한다.

이번 벤치는 Simulator 정지 후 백업/명시적 이관을 수행했다. virtual-axis-0/1의 새 0x6085는 raw 1000이다. 기존 21개 값은 모두 원본과 일치한다. Copley 두 파일은 바이트 단위로 변경되지 않았다.

## 실제 EtherCAT / Motion Server 시험

Windows Motion Server → 실축·실제 IO → Linux Soft ESC의 기존 8-Slave 케이블 구성을 사용했다. WKC 기대값은 24다. 실축에 이동/Enable 명령을 시험 클라이언트가 보내지 않았다. 기존 실축 Fault Reset과 전체 Disable은 수행했다. 서버 재시작 초기화의 자동 Enable은 기존 서버 동작이며, 테스트 종료 시 전체 Disable을 명시적으로 수행했다.

| 구성 | 실제 수행 | 결과 |
| --- | --- | --- |
| 기존 basic: F-KR 2축 + Copley 2축 + 가상 CPX 2개 | F-KR Homing, ±5mm PP, PV/Stop, Jog/Stop, PP Halt, Disable·Reset·참조 유지·재실행 방지 | 192개 상태 표본, WKC 불일치 0 |
| 임시 advanced: F-KR 3축 + Copley 1축 + 가상 CPX 2개 | 위 순서와 3축 각각 Quick Stop→Switch On Disabled→Reset/Enable, 이전 이동 자동 재개 없음 | 307개 상태 표본, WKC 불일치 0 |
| 원래 basic 혼합 구성 복원 | F-KR/Copley 4축 PP와 두 실린더 DO/DI 동시 왕복 6회 | 12.104초, 상태 표본 235개, feedback 249개, WKC 불일치 0 |
| 실제 SDO 영구 저장 | F-KR 0x6085를 raw 2345/3456으로 변경·저장 → 컨테이너 재생성 → Master 초기화 후 읽기 | 두 축 모두 복원 일치. 이후 원래 raw 1000으로 복원·저장 |

실축 관측 위치는 시험별 약 147.839~147.841mm 범위였으며 실축 이동을 시험하지 않았다. 이는 센서/서보 피드백 변동 범위의 관찰이지 실축의 위치 정확도 검증은 아니다.

최초 직접 Enable만으로 Homing을 시도한 시험은 Switch On Disabled에서 시작 순서를 충족하지 못했다. 기존 서버 Enable API는 0x000F만 쓰므로 **Reset(0x0006→0x0007 포함) → Enable → Homing**으로 시험 절차를 수정했다. basic 모드는 manualCW를 거부하므로 Quick Stop만 임시 advanced 모드에서 검증했다. 이 두 건을 디바이스 구현 실패나 지원 완료로 잘못 계산하지 않았다.

최초 임시 fixture 준비에서 Python 모듈 검색 경로가 누락되어 파일 생성이 실패했다. 운영 복원 경로가 정상 동작했으며, 준비 경로를 수정한 후 최종 3축 시험을 통과했다.
