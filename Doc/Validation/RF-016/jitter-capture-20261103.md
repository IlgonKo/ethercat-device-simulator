# RF-016 — Windows 송신 / Linux 수신 지터 비교 (2026-11-03)

- 문서 유형: **검증 기록**
- 관련: [RF-016](../../RF/RF-016-cia402-profile-adapter.md)
- 판정: 이번에 관측한 긴 LRW 간격은 Windows 송신 캡처 단계에 이미 존재. Motion Server/OS/Npcap/NIC 내부 원인은 미확정.

## 방법

현재 실제 축·IO + F-KR 2/Copley 2 혼합 버스, 4ms/basic/PP를 유지했다. Motion Server 코드·.env·컨테이너는 변경/재시작하지 않았다. Windows Npcap/dumpcap을 Master NIC에 수동 캡처로 연결했고 Linux는 운영 컨테이너의 별도 Python AF_PACKET 소켓으로 enp1s0 프레임을 읽으며 SO_TIMESTAMPNS 커널 타임스탬프를 수집했다. 캡처는 프레임 송신·NIC 설정 변경을 하지 않았다.

Windows LRW 송신 WKC=0, 반환=18. Linux 실제 장비 경유 LRW=6. LRW 인덱스 순서와 간격 패턴으로 대응시켰다. Windows와 Linux 시계가 약 17초 다르므로 양쪽 절대 시각 차이를 전송 지연으로 계산하지 않았다. 각 호스트에서 계산한 인접 프레임 간격을 비교했다. 하드웨어 timestamp나 정밀 동기화는 아니다.

첫 정지 캡처의 Windows 명령에서 미지원 -F 옵션으로 실패하여 -P로 다시 시작했다. Linux 125초 중 정상 Windows 65초와 겹치는 구간만 분석했다. 이동 캡처는 수정된 도구로 양쪽 모두 exit 0이었다. 실패한 실행을 성공한 2분 동시 캡처로 표현하지 않는다.

## 결과

| 정지 공통 64.968초 | 16,243 | 5.715ms | 5.726ms | 양쪽 0 |
| 이동 준비·복원 포함 공통 139.687초 | 34,833 | 18.943ms | 18.913ms | 양쪽 9 |
| 반복 이동 121.844초 내 | 간격 30,407개 | 11.311ms | 11.320ms | 양쪽 1 |

이동 본 시험은 가상축 1~4만 0↔10mm/10mm/s, 110편도(55왕복). 상태 조회 2,313회 WKC 불일치/Fault 없음. 전체 Windows 캡처 70,474패킷, 이 중 LRW 송신/반환 각각 34,901개, 반환 WKC는 모두 18이었다. Windows 캡처 drop=0, Linux packet socket drop=0. 기타 프레임을 LRW 주기 통계와 혼합하지 않았다.

가장 긴 이동 중 간격은 동일 idx=7 프레임으로 Windows 11.311054ms / Linux 11.320114ms, 차이 약 0.00906ms였다. 전체 공통 구간에서 양쪽 간격 차이 절댓값의 평균 0.00895ms, p99 0.03648ms. Linux 보조 캡처 프로세스의 kernel→userspace 지연은 평균 0.02070ms·최대 0.26679ms였다. 이는 Simulator 자체 read 지연 측정값은 아니다.

전체 캡처의 약 19ms 최대값은 준비 명령 구간이며 복원에도 약 14~15ms가 관측됐다. 이를 지속 이동 최대값으로 표현하지 않는다. 과거 10분 시험의 정확히 21.998ms 사건을 소급 추적한 것은 아니지만, 이번 재현된 긴 간격은 Linux 도착 이전부터 존재했다.

## 대응 방법과 한계

정지 구간은 첫 1000개 프레임 간격 패턴으로 인덱스 반복 후보를 비교했다(최적 RMS 0.015ms, 다음 후보 0.234ms). 이동 캡처는 양쪽 시작 시각이 달라 단순 시작 정렬을 폐기하고 정지 시험에서 얻은 시계 차이와 idx를 함께 사용했다. 약 -17.01초를 중심으로 ±15ms 안에서 같은 idx를 단조 대응했다. 재사용 주기 약64ms보다 좁은 범위이며 대응 구간 Windows LRW 누락 없이 연속임을 확인했다. Windows 선행 68개는 Linux 시작 전이라 대응에서 제외했다. 장기 시계 drift가 있어 절대 timestamp 차이는 편도 지연이 아니다.

Npcap 송신 timestamp는 송신 함수 진입 시각이나 NIC 하드웨어 실제 전송 시각과 동일하지 않다. 현재 증거는 Windows 송신 경로까지 원인 범위를 좁히며, 애플리케이션 명령/SDO 처리·스케줄링·드라이버 지연을 구별하지 못한다. 또한 Master가 이전 응답을 기다린 영향까지 분리하려면 송신 함수/이전 반환 타이밍 상관 분석이 필요하다. 네트워크와 Linux가 모든 상황에서 무관하다는 보장도 아니다.

## 복원 및 다음 항목

가상축 위치 0·속도 0, Profile Velocity 100, 원래 가감속 유지, Disable·조작권 반환, 버스 normal/WKC18/18 확인. 실제 축 명령·영구 저장은 하지 않았다.

사용자 결정에 따라 Motion Server가 비RT 환경인 현재 조건에서는 추가 지터 원인 조사를 진행하지 않는다. 현재 MOTION_SERVER_CYCLE_STATS_LOGS=0이며 이 작업에서 설정을 바꾸거나 Master를 재시작하지 않았다. 현 구조 2축/4축 동일 조건 비교는 별도 미검증 항목이며 RF-016은 진행 중을 유지한다.
