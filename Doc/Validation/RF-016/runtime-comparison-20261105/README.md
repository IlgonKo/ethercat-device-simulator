# RF-016·RF-012 2축/4축 Docker/native 물리 비교

- 문서 유형: 검증 기록
- 날짜: 2026-11-05
- 판정: RF-016 마지막 동일 조건 비교·이동 부하 항목 완료. RF-012 Docker/native 비교 완료. 새 PC 배포·동일 Edge Master 배치는 별도 잔여.

## 조건

- Windows Python 3.14.3 / PySOEM 1.1.13 전용 시험 Master, 4ms 설정. Motion Server 버스 해제와 Panel 정지는 사용자 확인 후 진행했다.
- 기존 물리 실축·IO + Linux 가상축. 2축은 F-KR/Copley 각 1축, 4축은 각 2축을 교대로 배치한다. 실제 축/IO 출력은 0으로 유지하며 가상축에만 Enable/Home/PP를 보냈다.
- 가상축 공통 Rx24/Tx14 기본 매핑. 0↔10000 raw PP 반복, 속도 raw 10, 가감속은 모델 기본값. F-KR은 Homing 참조 후 PP. 모든 가상축이 목표 오차≤2 raw·속도≤1 raw에 도달하면 다음 편도 이동을 시작한다.
- 정지/PP 각각 약30초 × 2회 반복. 순서: Docker2 → native2 → native4 → Docker4 → Docker4 → native4 → native2 → Docker2. 30초는 비교 표본이며 신규 내구성 합격 기준이 아니다.
- fresh 임시 상태/매핑 저장소를 매번 사용. 운영 .env·저장소는 공유하지 않았다. 실험 종료 후 원래 컨테이너를 재시작하고 running/healthy 확인. Motion Server는 사용자가 다시 연결해야 한다.
- Linux kernel 6.8.1-1015-realtime, 동일 Edge/NIC. 기존 다른 서비스가 실행 중인 환경이며 CPU 고정·독점 또는 실시간 우선순위 보장 시험은 아니다.
- native Python 3.12.3 / GCC13.3, Docker Python3.12.13 / GCC14.2. C++ Release(-O3), FMPy0.3.26, 같은 소스 및 동일 FMU 파일 SHA256 bb760d9de08aff700b067ab1d46a73e3fde4d36f511f5c5e23c39bd83a40a8e6. Docker는 host network·기존 권한 구성을 사용했다.
- 이미지 ethercat-device-simulator:rf014-verified, ID sha256:e98e42e25076a556dedcf282298565fe2bb27383560e2a6c28e36431138177b6. 소스 기준 adfa454.

## 정상 동작

총 측정 PDO 교환 **120,307회**, WKC 불일치 **0**, 가상축 Fault 표본 **0**. 2축 기대 WKC12, 4축18. PP 편도224회(112왕복) 모두 목표 도달. 선택한 C++ 계측 창의 IPC 실패0.

직접 PySOEM 시험이며 Motion Server의 API 명령 처리 성능을 측정한 것은 아니다. 시작/정리 구간은 위 교환 횟수에서 제외했다.

- C++/Python 1초 집계 창을 건수 가중 평균했다. Windows/Linux 시계 차이는 전후 SSH 왕복 측정으로 보정했다(약 -19.637초). 구간 앞뒤 1초를 제외하고 그 안에 완전히 포함된 창만 선택했다. 시계 차이를 전송 지연으로 해석하지 않는다.
- 모델 계산 합은 각 축의 평균 계산량 합계다. 서로 다른 집계 창 최대값을 합해 하나의 최악 주기라고 표현하지 않는다. 프레임 전체와 모델 계산/IPC 항목도 중첩되므로 더하지 않는다.
- 비동기 IPC 약3.95~3.97ms는 요청 제출부터 다음 pump에서 응답을 수거할 때까지다. 순수 소켓 왕복이나 FMU 계산 시간이 아니다.

## 해석

PP 이동 시 프레임 전체 평균은 Docker 2축0.053865ms/4축0.086792ms, native 2축0.054429ms/4축0.090547ms였다. 이번 조건에서 두 실행 방식의 C++ 처리 시간은 유사했고 4축으로 늘어도 통신/동작 실패가 없었다.

동작 모델 계산 평균 합은 Docker 0.100360→0.190138ms, native 0.092984→0.181540ms로 축 수에 따라 증가했다. Docker에서 약5~8% 큰 값이지만 Python 패치·컴파일러·사용자/컨테이너 환경 및 공유 호스트 부하가 다르므로 차이를 순수 컨테이너 오버헤드로 단정하지 않는다.

전체 C++ 선택 창 최대0.451899ms, master 송신 간격 최대11.386900ms, IPC 수거 최대9.145113ms. 평균 처리 시간이 작고 WKC가 정상이라는 결과가 매4ms 준수를 뜻하지 않는다. 비RT Master 지터 원인 조사는 사용자 결정대로 추가하지 않는다. 새로운 성능 최적화가 필요하다고 판정할 근거는 이번 시험에서 나오지 않았다.

## 준비 및 근거 한계

native 첫 준비 시 시험 저장 경로가 길어 Unix 소켓 경로 제한에 걸렸다. 임시 0700 디렉터리의 짧은 소켓 경로로 수정한 뒤 본 시험을 시작했다. 준비 실패는 집계에서 제외했다.

초기 config_init 메타데이터에서 일부 CPX의 vendor가0으로 반환됐다. 원본 result에 보존했다. 제품코드/리비전은 같았고 본 OP 측정의 기대 WKC·가상축 식별·동작은 정상이다. 이 자료로 CPX identity 검증 완료를 추가 주장하지 않는다.
