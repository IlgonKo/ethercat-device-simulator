# RF-022 — C++ FMU 전환 1~4단계

- 현재 상태: **검증 기록 — 1~4단계 통과**
- 일자: 2026-11-26
- 상위: [RF-022](../../RF/RF-022-f-kr-cmmt-fmu.md)
- 기준: RF-015 `88d7f40a30fb0733d14f674c9be10847b2f18bf9`, Linux Edge-ubuntu.
- 범위: 사용자가 승인한 구현 1~4단계. 운영 컨테이너·Motion Server·실제 축·state 파일은 변경하지 않았다.

## 구현

1. tests/reference에 Python adapter·servo·state machine을 보존했다. RF-015 정책 시험은 이 명시적 기준으로 유지하고 실제 FMU와의 별도 비교를 추가했다.
2. 공통 C++17 drive.hpp와 FMI 3.0 CS 연결을 구현했다. 직선 m 계열 / 회전 rad 계열의 두 산출물, native Linux x86-64 라이브러리 및 재빌드 가능한 소스를 포함한다. Python 내장 없음.
3. 제품 F-KR adapter는 같은 OD를 읽고 15개 입력을 설정한 뒤 기존 dt로 step, 4개 출력을 같은 OD에 반영한다. 기준 모델 속성 접근 없음. MODELS/MODES·저장 schema 3/23개 값·매핑 및 IPC 의미 유지.
4. Docker Builder에 빌드·검증을 넣었다. Runtime은 실행 라이브러리와 FMU만 포함한다. 외부 FMU override에는 해당 구성의 모든 산출물이 필요하다.

## 비교 기준과 결과

논리 상태/Mode는 각 주기 정확히 같아야 한다. 위치·속도·장치 target readback은 시험 전 정한 raw 1 LSB 이내이며, 양자화 전 값과 실제 SDO 인코딩 정수 모두 확인한다.

| 지표 | 직선 | 회전 |
| --- | --- | --- |
| 비교 tick | 3,300 | 3,146 |
| Statusword/Mode 불일치 | 0 | 0 |
| 양자화 전 raw 최대 차이 | 0 | 3.2742e-10 |
| 인코딩 후 정수 최대 차이 | 0 | 0 |
| 현재 위치 SI 최대 차이 | 0 m | 9.3259e-15 rad |
| 현재 속도 SI 최대 차이 | 0 m/s | 2.7756e-17 rad/s |

PP snapshot/이동 중 요청 무시·다음 운전 설정·완료, PV/Jog 반전·중립 재무장·한계, Halt/Disable/Quick Stop, 모드 전환, Homing 완료·취소·재Homing, 기존 CSP·OD target readback, 1~100 ms의 유효 step 및 200° 누적 회전을 포함한다. 새로운 modulo/물리 모델 기능은 없다.

## 자동 시험

- 실제 F-KR FMU 12개 시험: 동일 입력 비교·독립 인스턴스·재생성 초기 상태·독립 FMI 호출·오류 latch·누락/잘못된 차원 거부. native core Fault 주입/Reset·Homing 취소도 두 variant 빌드 때 확인.
- F-KR 4축의 NIC 없는 실제 Slave/OD/IPC 매핑·PP/재시작 시험 통과. 서로 다른 축의 OD/모델 상태를 공유하지 않음.
- Docker CTest 6/6, Python 단위 128개 중 127개 통과·1개 Windows PySOEM 의존 시험 건너뜀.
- 실제 IO FMU 12/12, Copley FMU 8/8, CPX NIC 없는 통신·채널 연결 회귀 통과.
- F-KR 4축 및 F-KR/Copley 혼합 4축 매핑·PP·저장 재시작, schema/checksum/논리 오류 복원 시험 통과.
- 실제 Slave/Model Host IPC 지연·timeout·SIGSTOP·종료·오래된 session/request·비활성 상태 timeout/정지 8개 시나리오 통과.
- 최종 Runtime 이미지를 network=none으로 실행하고 최신 비교 시험 12개를 읽기 전용으로 마운트해 재검증했다. 이미지 안의 FMU/실행 코드로 200° 누적 회전·재생성 및 위 표의 6,446 tick 비교 통과. 테스트 외 코드·FMU·운영 state를 호스트에서 마운트하지 않았다.
- g++로 같은 호스트에서 반복 빌드한 산출물 해시 일치. Docker Runtime에서 컴파일러 부재·libstdc++ 로드·Slave 동적 라이브러리 의존 확인 통과.

최종 빌드 로그: build/rf022-docker-verified.log. Runtime 보완 비교: build/rf022-runtime-fmu.log. 호스트 비교: build/rf022-comparison.json. 로그는 생성 결과이며 아래 수치/해시를 문서에 보존한다.

새 이미지 `ethercat-device-simulator:dev` ID: `sha256:503af1972240d73eddcd0879bedbbed347c9e8be80dcbe6c8be3e505fb9ceede`.
운영 컨테이너는 기존 `sha256:8c20f706a693327b3b64a3945b93da05ff4eadcec38b8891d1ae60907b68f657`로 running/healthy임을 확인했다.

F-KR native core Fault 주입은 테스트에서만 접근하는 내부 상태로 수행한다. 공개 FMU에 별도 Fault 주입/관리 입력을 추가하지 않았다. 현재 운전 모델에는 새로운 물리 Fault 발생원을 추가하지 않았다.

## 재현과 산출물

```bash
bash scripts/docker/build.sh
# 네이티브 독립 빌드 (g++ 및 잠긴 FMPy 환경 필요)
build/fmi-venv/bin/python scripts/models/build-f-kr-cmmt-fmus.py
RF022_REPORT=build/rf022-comparison.json PYTHONPATH=src:. \
  build/fmi-venv/bin/python -m unittest tests.integration.test_f_kr_fmu -v
```

각 FMU 옆 provenance.json에 소스·빌드 스크립트·산출물 SHA-256를 기록한다. Docker와 호스트의 컴파일러가 다르면 바이너리 해시는 달라질 수 있으며 같은 실행 계약/시험을 적용한다. 생성 FMU는 기존 정책대로 Git에 직접 추가하지 않고 소스·빌드 절차를 관리한다. 오프라인 묶음은 변경 파일을 Git에 등록·커밋한 뒤 기존 deployment 도구로 내보내야 소스와 repository.bundle 기준이 일치한다.

## 남은 범위

1~4단계 종료 시 남았던 실제 Motion Server 연결·직선/회전·다축·Copley/CPX/IO 혼합 운전, 저장/재시작·Host 장애 복구 및 처리 시간 비교는 후속 [5단계 보고서](stage5-20261126.md)에서 완료했다. 이 보고서는 물리 통신·WKC·실시간 성능 또는 장시간 수치 안정성을 보증하지 않는다. 새 이미지 생성과 운영 컨테이너 교체는 구분한다.
