# DT-003 — 장치 모델 경계와 FMI 확장

- 결정일: 2026-09-15
- 갱신일: 2026-10-26
- 상태: Co-Simulation 및 별도 Model Host 프로세스 채택, 통합 구현·장애 처리 계약은 후속

## 확정 방향

축·IO 장치 동작은 Omniverse가 아닌 시뮬레이션 모델에서 계산한다. 현재 가상축·가상 IO를 재사용하고 향후 Functional Mock-up Interface(FMI) 기반 모델과 호환할 수 있도록 어댑터 경계를 둔다. 현재 FMI 호환성이나 가상 IO의 EtherCAT·DT 연결이 검증되었다는 의미는 아니다.

## 계층

- KickCAT: EtherCAT 프레임, ESC, Mailbox 및 PDO 통신.
- 장치 계층: OD·CiA 402와 명령·상태 변환. 기존 VirtualOdBridge와 가상 서보의 역할을 분석해 경계를 정리한다.
- 실행 계층: 모델 초기화, 입력 적용, 시간 진행, 출력 수집, 리셋·종료.
- 모델 어댑터: 현재 가상축·가상 IO와 향후 FMI 모델을 내부 실행 계약에 연결.
- DT 연결: 라우터에서 선택된 피드백을 Omniverse에 표시. 장치 동작을 중복 계산하지 않음.

현재 C++ KickCAT ↔ Unix 소켓 ↔ Python 모델 구조를 출발점으로 사용한다. 공통 모델 패키지의 배포·의존성 경계는 후속 결정이며 Motion Server 제품 코드 변경이나 모델 코드의 무관리 복제를 전제로 하지 않는다.

## 전환용 관리 인터페이스

EtherCAT 명령 경로와 구분되는 모델 관리 인터페이스에서 정지 상태의 초기화를 제공한다. 위치만 덮어쓰지 않고 필요한 내부 상태·센서·출력 일관성을 검증한다. 장치 식별, 스냅샷 버전·시각·단위, 필수 값 검증, 적용 결과와 오류를 상세 계약에 포함한다. 구체적 전송 방식과 스키마는 미결정이다.

## 시간과 환경 입력

모델 계산 주기와 Omniverse 화면 갱신을 분리한다. 렌더링 속도가 모델 시간을 결정하지 않도록 한다. 모델 주기·외부 입력 샘플링·지연 처리의 상세 정책은 후속 설계에서 정한다.

Omniverse 접촉 이벤트나 사용자 조작을 모델의 환경 입력으로 전달하는 것은 향후 확장 후보이다. 역방향 연동을 초기 구현 완료 조건으로 간주하지 않는다. 도입 시에도 최종 장치 상태는 모델이 결정한다.

## FMI 실행 구조 결정 (2026-10-26)

FMI 실행 방식은 Co-Simulation을 채택한다. 어댑터는 재사용 가능한 라이브러리로 만들고, KickCAT과 분리된 Model Host 프로세스가 어댑터와 FMU를 로드한다. 초기 구현은 현재 Python 모델 서비스 구조를 출발점으로 삼는다. 라이브러리는 책임 경계를 뜻하며 어댑터를 반드시 C++ 공유 라이브러리로 구현한다는 결정은 아니다.

```text
Motion Server (기존 독립 패키지)
    │ 실제 EtherCAT
    ▼
프로세스 1: KickCAT Slave
    ESC / Mailbox / SDO / OD / PDO
    │ Unix 소켓 IPC
    ▼
프로세스 2: Model Host
    └─ 어댑터 라이브러리
         ├─ 장치별 OD ↔ 모델 변수 매핑·타입·단위 변환
         ├─ 초기화·파라미터 적용·시간 진행·출력 수집
         └─ 기존 자체 가상축 모델 또는 FMU 라이브러리(.so)
              FMI 입력 설정 → doStep → 출력 읽기
```

논리적으로 Slave·어댑터·모델의 세 계층이며 초기 실행 프로세스는 두 개다. FMU 자체는 독립 실행 프로그램이 아니다. 별도 FMU Runner 및 추가 IPC는 초기 구성에 도입하지 않는다. 기존 자체 모델과 FMU는 같은 축의 대체 실행 경로이며, 같은 축의 동작을 동시에 계산하지 않는다. 가상 IO는 RF-013의 보류 범위를 유지한다.

### 책임 경계

- KickCAT은 EtherCAT Slave 역할에 집중한다. 프레임·ESC·Mailbox·SDO 프로토콜·OD 접근·PDO 매핑을 담당하며 FMU 변수나 모터 계산을 직접 해석하지 않는다.
- 어댑터는 장치별 데이터 매핑과 모델 실행을 담당한다. 장치별 매핑과 공통 FMI 실행기를 분리해 Copley에서 향후 CMMT FMU로 교체할 수 있게 한다. 파라미터 저장·복원은 기존 DT-004/RF-010 정책을 적용한다.
- FMU는 제공된 제어기·모터 동작을 계산한다. FMU가 CiA402 상태 머신을 제공하면 ControlWord를 입력하고 StatusWord를 출력받으며 기존 가상축 상태 머신을 중복 실행하지 않는다. FMU에 없는 기능의 책임은 장치별로 명세한다.
- 모델에 연결된 SDO 쓰기는 어댑터·모델의 검증과 적용 결과를 반영해 응답해야 한다. OD 저장값과 모델 적용값이 성공 응답 후 서로 달라지지 않도록 상세 계약을 정한다. TD-001의 Abort 응답 호환성은 별도 보류 항목이다.

### 프로세스 분리 이유와 장애 처리 원칙

테스트 코드·어댑터·FMU의 오류, 프로세스 충돌 또는 무한 대기가 발생해도 EtherCAT Slave 프로세스까지 함께 종료되지 않게 하는 것이 목적이다. 모델 장애 중에도 통신부를 유지해 원인 확인과 복구가 가능하도록 한다. 단, 프로세스 분리 자체가 EtherCAT 주기 준수나 정상 응답을 보장하지는 않는다.

- IPC 응답 시간 제한을 두고 모델 응답을 무한정 기다리지 않는다. 통신 처리 지연을 제한하는 실행 순서도 함께 설계한다.
- 모델 계산 실패·응답 만료를 감지하고 장치 Fault 또는 정의된 통신 오류로 노출한다. 마지막 위치·상태를 계속 정상 피드백처럼 제공하지 않는다.
- 모델 재시작 후 장치 구성·파라미터·상태 일관성을 확인하고 명시적으로 복구한다. 이전 이동 명령이나 운전 상태를 자동으로 재개하지 않는다.
- 하나의 Model Host에 여러 축을 넣으면 Host 충돌은 그 안의 모든 축에 영향을 줄 수 있다. 초기 분리는 Slave와 모델 사이의 격리이며 축별 장애 격리까지 보장하지 않는다.
- Docker 배포도 이 원칙을 따라야 한다. Model Host 종료만으로 감독 프로그램이 Slave까지 종료하지 않도록 수명 주기 정책을 검증한다. 단일 컨테이너 결정은 유지한다.

이 항목은 설계 결정이다. 현재 코드에 위 시간 제한·장애 표시·복구 정책이 모두 구현됐다는 의미가 아니다. 구체적 timeout 값, Fault/AL 상태·SDO Abort 매핑, 피드백 유효성 표현, 장애 영향 범위와 복구 절차는 구현 전에 확정한다.

### 확인된 실행 가능성과 남은 검증

2026-10-26 Edge-ubuntu의 Linux x86_64에서 CopleyDriveSim 소스형 FMI 3.0 CS FMU를 모델 소스 수정 없이 GCC·공식 FMI 3.0.2 헤더로 빌드했다. 원본 자체 검사 14개가 통과했고 Python ctypes로 공유 라이브러리를 로드해 4개 인스턴스를 8 ms 계산 간격으로 실행했다. 서로 다른 PP 목표 위치 도달, 한 인스턴스의 Fault 주입 시 다른 인스턴스 상태 유지 및 Fault Reset을 확인했다.

- 원본 revision: `68978af04ea475cf89e39ae872cdccb5ddc95e4c`.
- [CopleyDriveSim 원본 및 설명](https://github.com/Beckhoff-USA-Community/AAG_TwinCAT_CiA402_CANopen_CPP_FMU_MATLAB/tree/68978af04ea475cf89e39ae872cdccb5ddc95e4c/MATLAB_and_Simulink/FMU_DriveSim).
- 시험은 FMU 단독 실행이며 KickCAT·EtherCAT 연동, 실시간 성능, 일반 FMU importer 호환성 또는 FMI 전체 적합성 검증이 아니다. Fault 입력 시험은 Host 충돌·무한 대기 격리 시험과 다르다.
- Copley 모델은 PP/PV/PT 등의 기능 모델이며 상세 모터 물리 모델이나 CMMT 제품 동작의 동등성을 보장하지 않는다. 초기 FMI 연동 검증 후보로 사용한다.

2026-10-26 우선순위 변경: 다음 구현은 공통 CiA402 Drive 프로파일과 F-KR Internal 어댑터 분리다. FMU 연동은 그 이후 진행한다. 이후 4축에서 IPC·FMU 계산·전체 주기 지연을 측정하고, Host 종료·응답 지연·FMU 오류 시 Slave 생존 및 장애 노출·명시적 복구를 검증한다. 현재의 가상축 경로도 회귀 검증한다.

제품에서 지원할 FMI 버전 범위(2.0/3.0), 변수형, 모델 수명 주기, 상태 초기화·복원 능력, 시간 진행 및 모델 배포 계약은 후속 명세한다. Copley 시험의 FMI 3.0 사용을 CMMT FMU 버전 확정으로 해석하지 않는다. 지원 모델의 초기화 능력이 모드 전환 정책을 충족하는지 별도 검증한다.

## 파라미터 영구 저장

재시작 때 장치 설정이 초기화되지 않도록 시뮬레이터가 안정적인 장치 ID 기반 영구 저장을 관리한다. 모델은 검증된 저장 설정으로 초기화하며 실행 상태는 별도 취급한다. [DT-004](DT-004-parameter-sync-persistence.md)의 기본값·영구 설정·실행 상태 경계 및 저장 실패 정책을 따른다. 향후 FMI 어댑터도 지원 가능한 파라미터 적용·복원 능력을 명시한다.

## CiA402 공통 프로파일 결정 (2026-10-26)

[DT-007](DT-007-cia402-profile-adapters.md)에 공통 프로파일·EtherCAT 장치 설명·모델 어댑터 분리 및 프로젝트 폴더 구조를 확정했다. 가상 디바이스는 EtherCAT Slave와 기능 모델로 구성하며, 기능 모델은 CiA402 Drive·모델별 어댑터·동작 모델을 포함한다. Python 패키지는 src/functional_model, C++는 src/ethercat_slave로 배치한다. 최초 대상은 자체 모델이며, 향후 FMI 공통 어댑터와 모델별 매핑을 우선하고 동작 차이가 있을 때만 전용 코드를 추가한다. [RF-016](../RF/RF-016-cia402-profile-adapter.md)으로 첫 구현 범위를 관리한다.
