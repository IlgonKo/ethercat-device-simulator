## 최신 결정 — 마지막 적용 매핑 유지·복원 (2026-11-03)

- **.env 초기 PDO 매핑 설정을 두지 않는다.** .env에서 매핑을 지정하거나 재시작 시 별도 기본 매핑으로 덮어쓰는 제안은 폐기한다.
- Master가 **PRE-OP에서 개별 Subindex SDO로 PDO mapping/assignment를 설정·재설정**할 수 있다. SAFE-OP·OP에서는 매핑 변경을 허용하지 않는다.
- 후보 설정은 SAFE-OP 전환 시 전체 검증 후 해당 Slave의 Rx·Tx 배치를 함께 적용한다. 실패 시 PRE-OP 및 프로세스를 유지하고 Master가 수정·재시도하거나 이전 구성을 명시적으로 재설정한다.
- **마지막으로 저장 확정한 PDO 매핑을 유지하고 영구 저장한다. Simulator 재시작 후에도 이 매핑을 복원한다.** 초기화 전용 별도 매핑과 운전용 매핑을 이중으로 관리하지 않는다.
- 단순히 PRE-OP으로 돌아왔다는 이유로 마지막 적용 매핑을 초기화하지 않는다. Master는 기존 구성을 읽거나 새 후보를 설정할 수 있다.
- 저장 확정 전 후보 작성·검증·준비 실패는 기존 저장본을 대체하지 않는다. 저장 확정 후 활성화 실패는 새 저장본을 유지하고 운전을 차단한다. 후보 설정 중 재시작한 경우에는 마지막 저장 확정 매핑을 복원한다.
- 매핑 복원이 Enable 또는 이전 이동의 자동 재개를 의미하지 않는다. 기존 Fault/운전 재개 정책 및 아래 PP 시작 요청 조건을 유지한다.
- 동일 OD 중복 매핑 및 Complete Access 읽기·쓰기 미지원 결정은 유지한다.
- 이전의 “.env 고정 매핑 / SDO 재설정 금지”와 “재시작 시 motion_server_default 복원” 제안은 철회한다. 아래 후보 설정·SAFE-OP 적용·실패 복원 정책은 현재 유효한 요구사항이다.

### 저장·복원 정책의 확정 범위

최초 실행은 매핑 미설정이며 마지막 저장 확정 매핑을 복구 기준으로 사용한다. Slave 내부에서 저장·활성화 완료 후 SAFE-OP을 허용한다. 기능 모델은 매핑을 저장하거나 활성화하지 않는다.

IPC는 장치 OD 정의·값 접근 및 동작 모델 계산 요청과 결과를 전달하며 PDO 매핑 정보나 매핑 준비/저장/활성화 요청을 포함하지 않는다. FMI는 어댑터↔동작 모델의 경계다.

## 합의한 매핑·파라미터 저장 분리 (2026-11-03)

- PDO mapping/assignment는 EtherCAT Slave가 별도 매핑 파일에 저장·복원한다.
- 장치 파라미터는 기능 모델이 state/<축 ID>.json 파라미터 파일에 저장·복원한다.
- 각 파일은 다른 데이터의 원본이며 사본이 아니다. 각 담당 모듈만 자신의 파일을 갱신한다.
- 매핑 저장이 미저장 파라미터를 저장하거나 파라미터 저장이 후보 매핑을 저장하지 않는다. 파일 간 통합 저장 트랜잭션은 없다.
- 각 저장 담당이 직렬화·임시 파일·원자 교체·동기화로 자기 파일의 일관성을 보장한다.
- 이전 통합 파일·단일 저장 모듈·기능 모델로 매핑 저장/복원 요청을 전달하는 제안은 폐기한다. 통합 파일 전체를 Slave로 옮기는 제안도 채택하지 않는다.
- 매핑 파일 경로·장치 연결 키는 기존 장치 식별·저장 규칙에 맞춰 구현에서 정한다. 별도의 사용자 결정 대기 항목으로 두지 않는다.

## 합의한 최초 실행 및 저장·활성화·복원 실패 처리 (2026-11-03)

### 최초 실행

- 저장된 매핑이 없으면 별도 기본 매핑을 만들지 않고 “매핑 미설정” 상태로 시작한다.
- mapping/assignment 객체는 존재하되 항목 개수는 0으로 제공한다.
- PRE-OP에서 개별 SDO 통신과 유효한 장치 파라미터 접근을 허용한다.
- Master가 유효한 Rx·Tx 구성을 설정하고 저장·활성화가 완료되기 전에는 SAFE-OP 전환을 거부한다.
- 기존 Motion Server의 clear/rewrite 초기화가 최초 매핑 설정 경로다. 구버전 파일이 새 스키마와 호환되지 않으면 오류 처리한다. 자동 이관이나 기본값 대체는 하지 않는다.

### 저장 확정과 활성화 순서

1. 후보 Rx·Tx 전체 검증.
2. 이전 주기 요청 처리 정리.
3. Slave 내부에서 새 Rx·Tx 해석/조립 구성을 준비한다. 실패 가능한 검증·할당은 가능한 한 이 단계에서 완료한다.
4. Slave가 별도 매핑 파일을 저장 확정한다. 파라미터 파일은 변경하지 않는다.
5. Slave 내부에서 Rx·Tx 새 매핑을 함께 활성화하고 완료를 확인한다.
6. SAFE-OP 진입 허용.

**저장 확정이 새 매핑의 복구 기준을 바꾸는 commit 시점**이다. 기존의 “마지막 적용 성공 매핑”은 앞으로 “마지막 저장 확정 매핑”으로 표현한다. 저장 이후 런타임 활성화나 Master의 성공 응답 관측 전에 종료되면, 실제 운전에 사용되지 않은 새 매핑이 다음 시작에서 복원될 수 있다. Slave 내부 매핑 활성화 완료 전에는 운전을 허용하지 않는다.

| 실패 시점 | 합의한 처리 |
| --- | --- |
| 검증·준비·저장 확정 전 | 기존 저장본 보존, PRE-OP 유지, 수정·재시도. 새 매핑 활성화 금지 |
| 저장 확정 후 활성화 실패 | 새 저장본 유지, 운전 차단·진단 표시. 이전 매핑 자동 복귀 금지 |
| 저장 확정 후 프로세스 종료 | 재시작 시 새 저장본 검증·복원 |
| SAFE-OP 성공 응답 전 연결 종료 | Master가 후보 매핑 readback과 AL 상태를 함께 확인. readback만으로 저장·활성화 성공을 판단하지 않음 |

임시 파일과 원자 교체는 매핑 파일의 안전한 갱신 수단이며 별도 원본 사본을 뜻하지 않는다. 파일/디렉터리 동기화까지 고려하여 저장 완료를 확인한다. rename 이후 fsync 실패처럼 commit 결과를 확정할 수 없는 오류는 무조건 “기존 파일 보존”으로 보고하지 않는다. 저장본 확인·운전 차단·진단의 구체적 처리는 구현 오류표에 명시한다.

### 복원 실패

- 장치 파라미터는 유효하나 매핑이 없으면 매핑 미설정 상태에서 Master 설정을 기다린다.
- 파라미터는 유효하지만 매핑이 현재 프로파일/동작 모델 조건에 부적합하면 진단을 남기고 매핑 미설정 PRE-OP에서 Master 재설정을 허용한다. 새 구성 저장·활성화 시 해당 매핑 오류 원인의 해소를 확인한다.
- 어느 저장 파일이든 전체 손상·파싱 실패·비호환이거나 파라미터 복원 불가이면 자동 초기화·덮어쓰기를 하지 않는다. 원본을 보존하고 운전을 차단한 뒤 수동 복구한다. 정상 파라미터가 있는 것처럼 동작 모델을 실행하지 않는다.
- 잘못된 매핑을 임의의 기본 매핑으로 대체하지 않는다. 원본 보존/백업의 구체적 절차는 저장 스키마·복구 도구와 함께 정한다.
- 매핑 복원이 Enable 또는 이전 이동의 자동 재개를 의미하지 않는다.

## 확정한 저장 파일 호환성 정책 (2026-11-03)

- 저장 파일의 schema_version 또는 장치/동작 모델 식별 등 필수 호환 조건이 맞지 않으면 오류로 처리한다.
- 제품은 자동 이관·자동 초기화·자동 덮어쓰기를 수행하지 않는다. 별도의 이관 명령도 구현하지 않는다. 이전의 자동/명시적 이관 제안은 철회한다.
- 호환되지 않는 파일을 “매핑만 없음”으로 간주하여 운전을 진행하지 않는다. 원본을 보존하고 운전을 차단한다.
- 파라미터 파일이 유효하고 매핑 파일이 없거나, 매핑 파일의 스키마·식별·무결성은 유효하나 매핑 내용만 부적합한 경우는 기존에 합의한 매핑 미설정/복원 실패 정책을 따른다. 구버전 스키마 비호환과 구분한다.
- **이번 개발 전환에 한해서** 사용자는 현재 파라미터 보존 없이 새 형식으로 초기화하는 것을 허용했다. 이는 과거 통합 형식 제안 당시의 허용이며 이번 저장 분리를 위한 필수 초기화 작업이 아니다. 기존 파라미터는 유지한다. 이 허용을 제품의 비호환 파일 자동 초기화로 구현하지 않는다.
- 현재 설계 문서 갱신 단계에서는 실제 저장 파일을 변경하거나 삭제하지 않는다.

## 분리된 저장 파일의 형식 및 검사 (2026-11-03)

통합 파일의 parameters/pdo_mapping 영역 구성안은 폐기한다. 기존 파라미터 저장 형식은 기능 모델이 관리하며 RF-014 때문에 통합 스키마로 변경하지 않는다.

별도 매핑 파일은 schema_version, identity, revision, rx, tx, checksum 정보를 갖도록 설계한다. 구현은 매핑 스키마 1, 안정된 장치 id, STATE_DIR/pdo-mappings/<장치 id UTF-8 hex>.json을 사용한다. revision은 Slave의 저장 확정 번호이며 IPC에 전달하지 않는다.

Rx/Tx 배열은 순서 있는 32비트 CoE 매핑 값으로 index/subindex/bit_length를 저장한다. assignment/PDO 주소는 1차 고정 범위인 Rx 0x1C12/0x1600, Tx 0x1C13/0x1A00이며 스키마에서 결정된다. 배열 순서가 배치 순서다. 오프셋·항목 개수·총 바이트 수는 복원 시 계산한다. Padding은 index=0/subindex=0/8비트 배수 길이로 표현한다. checksum은 checksum 필드를 제외한 정렬된 JSON 전체의 CRC32이며 보안 인증용이 아닌 저장 무결성 검사다.

- 신규 파라미터 파일 생성·기본값 초기화는 기존 기능 모델의 파라미터 정책을 따른다.
- 매핑 파일이 없으면 매핑 미설정 상태로 시작한다. 기본 매핑을 생성하지 않는다.
- 각 파일의 비호환·전체 손상·무결성 실패는 원본 보존 및 초기화 실패로 처리한다. 자동 이관·초기화·덮어쓰기 없음.
- 매핑 파일 형식·식별·무결성은 유효하지만 현재 프로파일의 매핑 조건에 맞지 않으면 진단을 남기고 매핑 미설정 PRE-OP에서 Master 재설정을 기다린다.
- 이번 개발 전환의 기존 데이터 폐기 허용은 제품의 일반 복구 정책이 아니다. 설계 문서 갱신 단계에서는 저장 파일을 변경하지 않는다.

## 문제와 목표

현재 지원 범위는 motion_server_default(Rx 24 / Tx 14바이트)의 동일 구성 clear/rewrite/restore이다. RF 등록 당시에는 다른 매핑 값의 FixedMapping 검사 실패·종료 경로가 문제로 기록됐다. 이후 Fault/SDO 처리 변경이 있으므로 상세 거부 경로는 구현 전 현재 코드에서 재확인한다. 기본 매핑의 성공이나 오류 격리가 임의 재매핑 지원을 의미하지 않는다.

Master가 SDO로 장치가 지원하는 범위의 PDO 항목·순서·구성을 변경하면, 검증 후 실제 process image와 모델 연결을 새 배치에 맞춰 동작시키는 것이 목표다. '동적'은 지원 상태에서 수행하는 재매핑을 뜻하며 OP 중 임의 실시간 변경이나 모든 OD 매핑을 허용한다는 의미가 아니다.

## 합의한 전체 구조 및 책임 경계 (2026-11-03)

### 용어와 프로세스

- **가상장치:** EtherCAT Slave와 기능 모델(Functional Model)을 합친 논리 장치.
- **기능 모델:** CiA402 Drive의 Profile·장치 OD 값 저장소·모델별 어댑터·동작 모델과 저장 기능을 포함하는 상위 구성.
- **동작 모델(Behaviour Model):** F-KR CMMT 또는 Copley FMU/향후 CMMT FMU처럼 동작·상태 변화를 계산하는 구성. 앞으로 계산 대상으로 쓰는 “모델”은 “동작 모델”로 표현하여 기능 모델과 구분한다.
- **어댑터:** OD와 동작 모델 변수의 연결·단위 변환·동작 모델별 지원 조건 처리 담당.
- 별도의 “축 실행부”라는 설계 모듈을 추가하지 않는다. 기존 runtime 클래스의 구현상 생성/호출 위치와 이 논리적 책임 구분을 혼동하지 않는다.

```text
               ↕ EtherCAT
가상장치

│  │  ├─ 통신 객체 → 매핑 관리자
│  │  └─ 장치 객체 → IPC로 위임
│  ├─ PDO 매핑 관리·검증
│  ├─ PDO 해석·조립
│  └─ 매핑 저장·복원 ↔ 별도 매핑 파일
│               ↕ IPC
└─ 기능 모델(Functional Model) 프로세스
   ├─ CiA402 Drive
   │  ├─ Profile — 장치 OD 정의·타입·접근 권한
   │  ├─ 장치 OD 값 저장소 — 현재 값
   │  └─ 모델별 Adapter
   │          ↕ FMI / 내부 호출
   │      동작 모델(Behaviour Model)
   │      ├─ F-KR CMMT
   │      └─ Copley FMU / 향후 CMMT FMU
   └─ 파라미터 저장·복원 ↔ state/<축 ID>.json 파라미터 파일
```

장치 하나의 논리 구조를 표시한 것이다. 여러 가상장치는 기존 두 프로세스 안에서 관리하며 장치마다 프로세스를 새로 만든다는 의미는 아니다. 장치별 OD 값·매핑·동작 모델 인스턴스·저장 연결은 독립적이다.

### 하나의 논리 OD와 객체별 담당

Master에 제공하는 OD 주소 공간과 접근 창구는 가상장치당 하나다. 독립된 두 OD를 노출하거나 같은 객체의 값을 양쪽에서 독립적으로 관리하지 않는다. 두 프로세스가 물리적으로 하나의 메모리 저장소를 공유한다는 의미도 아니다.

| 객체 | 예시 | 상태/값 소유·처리 담당 |
| --- | --- | --- |
| 통신 객체 | PDO mapping·assignment | EtherCAT Slave의 매핑 관리자 |
| 장치 명령·설정 | Controlword·Mode·Target Position·Profile Velocity | 기능 모델의 CiA402 Drive 공통 장치 OD 값 저장소; 어댑터가 의미/지원 조건 처리 |
| 장치 피드백 | Statusword·Actual Position·Actual Velocity | 같은 장치 OD 값 저장소; 어댑터가 동작 모델 계산 결과로 갱신 |

Profile은 항목 정의·타입·길이·접근 권한·매핑 가능 여부를 제공한다. 값 저장소는 장치별 현재 값을 보관한다. 정의를 공유하더라도 값 인스턴스는 장치별로 분리한다. Slave의 접근 검증에 필요한 메타데이터는 해당 계약으로 공급하고 중복 정의의 불일치를 방지한다.

### 주기 데이터와 SDO 흐름

1. Slave가 현재 적용 매핑으로 RxPDO를 해석한다.
2. 수신 장치 객체 값을 IPC 요청에 묶어 기능 모델 프로세스로 전달한다.
3. 기능 모델은 수신 항목만 장치 OD에 갱신한다. PDO에서 제외된 항목은 SDO 설정값을 유지한다.
4. 어댑터가 필요한 OD 입력을 **동작 모델**에 전달하고 동작 모델 계산을 수행한다.
5. 어댑터가 동작 모델 피드백을 같은 장치 OD에 반영한다.
6. TxPDO 대상 OD 값을 묶어 Slave에 반환하고, Slave가 현재 배치에 맞게 송신 PDO를 조립한다.

SDO 장치 객체 접근도 같은 OD 값을 사용한다. 매 주기 OD 값을 읽고 갱신하되 OD 항목마다 별도 IPC 호출을 만들지 않는다. FMI는 어댑터와 FMU 동작 모델 사이의 인터페이스이며 두 프로세스 사이 IPC를 대체하지 않는다.

현재 F-KR 동작 모델 내부와 Copley 어댑터 내부의 장치 OD 소유권을 CiA402 Drive 공통 계층으로 통일한다. 어댑터와 F-KR 동작 모델은 같은 OD 인스턴스를 참조하도록 연결하고 독립 사본을 만들지 않는다. FMU 내부 계산 상태는 별도로 존재할 수 있지만 외부에 제공하는 CiA402 장치 값의 기준은 공통 OD이다.

### 매핑 설정 및 영구 저장 흐름

- PRE-OP에서 Master가 개별 SDO 쓰기로 후보 매핑을 작성한다.
- SAFE-OP 전환 시 Slave가 전체 검증·이전 요청 정리·새 배치 준비·매핑 파일 저장·Rx/Tx 활성화를 수행한다.
- 재시작 시 Slave가 자기 매핑 파일을 검증·복원하고 기능 모델은 자기 파라미터 파일을 복원한다.
- 장치 OD 값 저장소는 현재 값을 담는 메모리다. 영구 저장은 각 담당 파일에서 독립적으로 처리한다.
- 기능 모델은 PDO 배치나 매핑 전환을 알 필요가 없으며 매핑 준비·저장·활성화 IPC는 두지 않는다.

### 합의한 IPC 계약 (2026-11-03)

| 구분 | 합의 내용 |
| --- | --- |
| OD 정의 조회 | OD 주소·타입·접근 권한 등 프로파일 메타데이터. 실제 PDO 배치 전달 없음 |
| 주기 요청 | 장치·세션·요청 식별자, 갱신할 OD 주소와 값, 계산 시간 정보 및 조회할 OD 주소를 묶어 전달 |
| 주기 응답 | 해당 요청 식별자, 조회한 OD 주소와 값 및 진단 상태 반환 |
| SDO 장치 객체 접근 | 같은 장치 OD 읽기·쓰기. 실제 반영 완료 뒤 성공 응답 |
| 매핑 관련 정보 | mapping/assignment 내용·오프셋·매핑 세대 및 준비/저장/활성화 요청 모두 제외 |
| 지연 응답 | Slave가 요청·세션을 대조하고 이전 요청을 정리하여 이전 응답을 새 TxPDO에 사용하지 않음 |

Slave가 매핑으로부터 OD 접근 목록을 만들되 기능 모델에는 일반 OD 접근으로 전달한다. 누락 Rx는 갱신하지 않으며 장치별 SDO/주기 처리 순서를 유지한다. 매핑 세대 관리가 필요하면 Slave 내부에만 둔다.

재매핑 전 이전 요청이 기능 모델에서 처리 완료됐음을 Slave가 확인한다. 응답을 버리는 것만으로 원격 OD 변경·계산이 취소된 것으로 간주하지 않는다. 처리 완료를 확인하지 못하면 새 매핑으로 운전을 허용하지 않는다. 기능 모델에 새 매핑 준비/활성화를 요청하지 않는다. 실제 IPC 장애는 RF-018 Host Fault 정책을 유지한다. PP 시작 재준비 조건은 아래 정책을 따르며 매핑 명령을 IPC에 추가하는 근거로 사용하지 않는다. 구현은 비활성 exchange 응답 완료를 SAFE-OP 전환의 선행 조건으로 사용한다. exchange는 session/request_id, active, values(index/subindex/data), reads(index/subindex)를 사용한다. values의 data는 해당 OD 바이트의 hex 표현이며 PDO 배치를 담지 않는다.

FMI는 어댑터와 동작 모델 사이의 호출이며 이 IPC와 구분한다.

## 합의한 SDO 반영 및 이전 목표값 처리 (2026-11-03)

### PDO에서 제외 가능한 항목

Mode of Operation, Target Position, Profile Velocity는 PDO에서 제외하고 SDO로 설정하는 것을 허용한다. PDO에서 제외돼도 OD는 존재한다. 이 결정이 모든 OD의 매핑 지원을 의미하지는 않는다. 이후 PDO 구성 범위 합의에서 Controlword/Statusword를 필수로 확정했다.

### 쓰기 완료와 모델 적용 시점

1. SDO 쓰기 수신 시 타입·길이·범위·현재 상태에서의 허용 여부를 검증한다.
2. 해당 축의 기능 모델 OD에 반영을 완료한 뒤 SDO 성공 응답을 보낸다. Slave의 큐에 넣었다는 이유만으로 성공을 응답하지 않는다.
3. 성공 이후의 SDO 읽기는 반영된 값을 반환한다. 이후 정상적인 PDO/SDO 쓰기로 다시 변경된 경우에는 그 최신 값을 반환한다.
4. 동작 모델에는 다음 계산 주기 시작부터 반영한다. 축별 SDO 쓰기와 동작 모델 계산의 실행 순서를 보장하여 계산 도중 일부 값이 바뀌지 않도록 한다.
5. 여러 SDO 쓰기는 각각 독립 요청이며 하나의 묶음으로 원자 적용된다는 보장은 없다. 권장 명령 순서는 Mode → Profile Velocity → Target Position의 쓰기 완료 확인 → Controlword로 이동 시작이다.

SDO/PDO는 별도 파라미터 사본을 소유하지 않고 같은 장치 OD 값을 갱신한다. PDO에 포함된 항목을 SDO로 써도 다음 수신 PDO가 다시 갱신할 수 있다. PDO에서 제외된 항목은 PDO 변환부가 건드리지 않으며 SDO로 설정된 OD 값을 유지한다. 동시 요청은 축별 처리 순서에 따르고 적용된 값의 순서를 일관되게 유지한다.

### PP 목표값과 실행 상태

OD의 설정 목표값과 현재 실행 중인 이동의 목표값을 구분한다. 이는 독립적인 파라미터 저장소를 두 개 만든다는 뜻이 아니라 설정값과 실행 상태를 구분한다는 뜻이다.

| 상황 | 합의한 처리 |
| --- | --- |
| 정지 중 Target Position SDO 쓰기 | OD 값만 변경하며 이동을 시작하지 않음 |
| 이동 중 Target Position SDO 쓰기 | OD 값만 변경하며 진행 중인 이동 목표는 유지 |
| 새로운 PP 시작 요청 수락 | 수락 시점의 Target Position을 실행 목표로 사용 |
| 재매핑으로 Target Position 제외 | OD 값 유지. 0이나 현재 위치로 자동 변경하지 않음 |
| 재매핑 후 운전 재개 | 이전 이동 자동 재개 금지. 새로운 PP 시작 요청을 기다림 |

운전 비활성화 시 어댑터가 처리 중인 이동 요청과 대기 요청을 무효화한다. 이 동작은 매핑 변경 여부와 무관한 공통 운전 수명주기 규칙으로 적용한다. IPC는 운전 활성/비활성 상태를 전달할 수 있으나 매핑 정보를 전달하지 않는다. Controlword의 시작 비트가 계속 켜져 있다는 이유로 재출발하지 않으며 새로운 PP 시작 요청의 edge를 확인한다. 재매핑이 Enable 또는 새 이동을 자동 발생시키지 않아야 한다. 운전 재활성화 이후 시작 비트 0을 확인한 뒤 새 0→1 변화만 시작 요청으로 인정한다. 요청 무효화의 구체적인 코드 지점과 어댑터 연결은 구현 설계에서 정한다.

이 PP 규칙은 F-KR 및 Copley 어댑터에서 일관되게 보장한다. EtherCAT Slave는 매핑과 데이터 전달을 담당하고 동작 모델의 동작 정책을 별도로 복제하지 않는다. 기존 동작 모델/FMU가 해당 규칙을 그대로 제공하는지는 구현 시 확인하고 어댑터 경계에서 보장한다.

### Mode 및 Profile Velocity

- Mode: 검증을 통과한 값을 다음 동작 모델 계산 주기에 전달한다. 미지원 모드 또는 전환 불가 상태의 요청은 거부하고 기존 값을 유지한다.
- Profile Velocity: OD에는 쓰기 완료 시 반영한다. 진행 중인 이동 속도에도 즉시 영향을 주는지는 해당 동작 모델의 기존 동작 규칙을 따른다. SDO/PDO라는 설정 경로 차이만으로 동작 의미를 바꾸지 않는다.
- 모델의 미지원 운전 모드 처리와 PDO 항목의 매핑 가능 여부는 별도로 판단한다.

## 합의한 재매핑 적용·실패 복원 정책 (2026-11-03)

매핑 설정 중인 후보 구성과 현재 적용된 구성을 Slave별로 분리한다. 후보 구성이 작성되는 동안 기존 적용 배치를 부분적으로 변경하지 않는다.

| 단계 | 합의한 처리 |
| --- | --- |
| 설정 시작 | PRE-OP에서만 매핑 변경 허용. 적용된 구성과 별도로 후보 작성 |
| SDO 쓰기 | 개별 요청 검증 후 후보에 반영. 잘못된 요청은 정상 SDO Abort로 거부하며 거부한 쓰기를 반영하지 않음 |
| 매핑 OD 조회 | Master가 작성 중인 후보 구성을 반환. 후보가 적용 완료됐다는 의미는 아님 |
| 적용 요청 | SAFE-OP 전환 요청을 전체 검증·적용의 기준으로 사용 |
| 적용 성공 | 해당 Slave의 Rx·Tx 구성과 변환 배치를 함께 적용한 뒤 SAFE-OP 진입 허용. 한쪽만 새 배치를 사용하는 상태를 노출하지 않음 |
| 전체 검증 실패 | SAFE-OP 전환을 거부하고 PRE-OP 유지. Slave·모델 프로세스를 종료하지 않음 |
| 수정·재시도 | Master가 후보를 수정한 뒤 상태 전환을 다시 요청 |
| 이전 구성 복원 | Master가 이전 매핑을 명시적으로 다시 설정하고 상태 전환을 요청. 자동으로 이전 배치로 되돌려 운전하지 않음 |

개별 SDO 요청 거부와 EtherCAT 상태 전환 거부는 다른 응답 경로이다. 적용 단계 실패는 상태 전환 거부로 표시하고, 정확한 SDO Abort/AL 상태 코드 대응은 구현 전 검증 표에서 정한다. 앞서 성공한 후보 설정 SDO를 적용 실패 때문에 소급하여 실패로 취급하지 않는다.

이전 유효 구성을 내부적으로 유지하더라도 Master와 합의 없이 그 배치로 운전을 계속하지 않는다. 실패한 후보는 Master가 읽고 수정할 수 있도록 하며, 재설정 중 후보 값을 이전 구성으로 몰래 바꾸지 않는다. 전체 적용 단위는 Slave별 Rx·Tx 한 쌍이며 여러 Slave 전체를 하나의 원자적 변경으로 처리한다는 의미는 아니다.

### PP 시작 요청 재준비

재매핑 후에는 시작 비트가 0인 요청을 확인한 다음 새로운 0→1 변화를 받아야 PP 시작을 허용한다. 기존 Controlword에서 시작 비트 1이 유지된 상태는 새로운 요청으로 인정하지 않는다. 이 조건은 정상적인 Drive Enable/운전 상태 조건을 대체하지 않으며, SAFE-OP 진입 또는 매핑 성공 자체가 이동을 시작하지 않는다.

## 확정한 미지원 항목 (2026-11-03)

- **동일 OD 중복 매핑 미지원:** 동일 방향의 적용 PDO 집합에서 같은 Index/Subindex를 반복해서 매핑하는 구성은 거부한다. 1차 구현에만 한정한 제한이나 후속 지원 예정 항목으로 두지 않는다. Padding은 실제 OD가 아니므로 별도 규칙으로 다룬다. 동일 OD의 Rx/Tx 양방향 허용 여부는 OD별 방향 정의에서 정하며, 이 중복 제한만으로 양방향 지원을 추가하지 않는다.
- **Complete Access 읽기·쓰기 미지원:** 개별 Subindex SDO 읽기·쓰기로 조회·설정한다. Complete Access 읽기와 쓰기 요청은 정상 SDO Abort로 거부하며 OD 값 및 후보/적용 구성을 변경하지 않는다. 후속 지원 예정으로 등록하지 않는다.
- 사용자 추가 결정에 따라 Complete Access 읽기를 유지한다는 이전 제안은 철회한다. EtherCAT Slave의 CoE SDO Complete Access 읽기·쓰기를 모두 미지원으로 한다. Master의 OD/PDO 탐색도 개별 Subindex 접근으로 가능한지 구현 시 확인한다. 현재 SOEM/PySOEM의 Complete Access 사용 여부와 Slave의 지원 광고 정보(ESI/SII/CoE 상세 정보 등)를 점검하고, 미지원 표시와 실제 응답을 일치시킨다. 기존 탐색 성공을 변경 후 호환성 근거로 대신하지 않는다.

## 합의한 1차 PDO 구성 범위 (2026-11-03)

| 항목 | 합의 내용 |
| --- | --- |
| PDO 개수 | Slave당 RxPDO 1개·TxPDO 1개 |
| 매핑 대상 | 현재 기본 PDO의 OD 항목부터 지원. 항목 순서·구성 변경 허용 |
| 필수 항목 | Rx Controlword·Tx Statusword |
| 선택 항목 | 나머지는 제외 가능. 선택 Rx는 기능 모델의 장치 OD 값 유지, 선택 Tx는 모델에서 갱신하되 PDO 송신만 생략 |
| 정렬 | 바이트 단위 항목만 지원 |
| Padding | 8비트 배수 허용. Rx padding은 무시하고 Tx padding은 0으로 채움. 실제 OD가 아니므로 동일 OD 중복 제한과 구분 |
| 최대 항목 수·바이트 수 | Slave별 Rx/Tx 각각 최대 64바이트·16항목. padding 포함, count subindex 0은 항목 수에서 제외 |

복수 PDO 지원 없이도 각 PDO 내부의 항목 순서와 구성을 변경할 수 있다. 기존 합의대로 동일 OD 중복 매핑과 Complete Access 읽기·쓰기는 지원하지 않는다. 매핑 가능하다는 사실이 해당 모델의 모든 운전 모드나 물리 기능 지원을 의미하지는 않는다.

## 확정한 설계와 구현 확인 항목

SDO 반영 시점과 선택 Rx 값 유지·PP 목표 처리 정책은 위와 같이 합의했다. 재매핑 적용·실패 복원 및 PP 재시작 edge 조건도 합의했다. 1차 지원 항목 범위·필수 항목·PDO 개수·정렬·padding도 합의했다. 마지막 저장 확정 매핑의 영구 저장·재시작 복원도 합의했다. PDO당 64바이트·16항목 상한도 합의했다. 정확한 오류 코드·상태/진단 반영 및 메시지/파일 필드 등은 상세 결정 사항이다.

| 순서 | 결정 사항 | 제안 및 확인할 경계 |
| --- | --- | --- |
| 1 | 매핑 가능한 OD와 필수/선택 구분 | 합의 완료: 현재 기본 PDO 항목부터 지원. Rx Controlword / Tx Statusword 필수, 나머지 제외 가능. 상세 Index/Subindex·타입·길이는 기존 프로파일과 대조해 지원표로 작성 |
| 2 | PDO에서 빠진 항목 처리·값 소유권 | 선택 Rx 값 유지·SDO 반영 시점·PP 목표값 처리 합의 완료(위 절). 선택 Tx는 모델에서 갱신하되 송신만 생략하도록 합의. 누락 Rx는 갱신하지 않으며 OD 주소 기반 IPC 계약에 따라 주기 값을 전달. 구체적인 직렬화 표현은 상세 설계 |
| 3 | 재설정 절차·적용 시점·실패 복원 | 합의 완료: PRE-OP 후보 작성/조회, SAFE-OP 전환 시 전체 검증 및 Slave별 Rx·Tx 함께 적용. 실패 시 PRE-OP 유지, Master가 수정 또는 이전 매핑 재설정. 자동 rollback 운전 없음. 정확한 오류 코드와 적용 구현 지점은 상세 설계 |
| 4 | 첫 지원 매핑 형식·상한 | 합의 완료: RxPDO 1개/TxPDO 1개, 바이트 단위 항목·8비트 배수 padding. 최대 크기 64바이트·최대 16항목(padding 포함)으로 확정. 동일 OD 중복 매핑과 Complete Access 읽기·쓰기는 미지원 |
| 5 | 초기화·재시작·모델별 지원·검증 계약 | 합의 완료: 마지막 저장 확정 매핑 영구 저장·재시작 복원, .env 초기 매핑 없음. 최초 실행·저장/적용 실패·복원 유효성·OD 소유권과 IPC 원칙 합의 완료; 메시지 형식·저장/활성화 실패 경계는 상세 결정 |

오류 유형별 처리 원칙은 합의했다. 매핑·파라미터 분리 저장 및 각 담당의 저장·복원 책임까지 합의했다. IPC의 구체적인 메시지 표현과 요청/응답 연결 방식은 합의된 경계에 맞춰 구현에서 정한다. 이후 상세 수치 오류 코드를 구현 전 대조한다. IPC의 기본 교환/식별/전환 원칙은 합의했으며 구체적인 메시지 표현은 상세 설계에서 정한다. 상한은 64바이트·16항목으로 확정했으며 상세 오류 코드는 코드와 프로토콜 근거를 확인해 정한다. 매핑 적용 시 OD 참조·오프셋·변환 목록을 계산하고 주기 처리에서 재사용하는 방식을 제안한다. 재매핑이 Enable 또는 새 이동 명령을 자동 발생시키지 않아야 한다.

## 작업 범위

- 기존 PDO의 회귀 시험 기준과 가상축 프로파일별 매핑 가능한 OD 항목, 방향·비트 길이·접근 조건·크기 상한을 정의한다.
- PDO mapping/assignment 객체의 SDO 쓰기 및 count clear/restore 절차를 처리한다. 매핑 변경은 PRE-OP에 한정하며 적용은 SAFE-OP 전환 시 위 합의에 따른다.
- 새로운 RxPDO/TxPDO의 길이·순서·오프셋 및 필요한 SyncManager/FMMU 연계를 처리한다.
- Slave의 PDO 변환부에서 Master 측 배치와 공통 모델 데이터 계약을 연결한다. IPC는 매핑 정보 없는 OD 주소·값 교환으로 변경한다. 메타데이터만 변경하고 wire 데이터를 기존 고정 배치로 해석하는 방식은 사용하지 않는다.
- 불완전한 재설정·미지원 항목·방향/길이 오류·잘못된 상태 요청을 정의된 오류로 거부한다. 개별 쓰기는 Abort로 거부하고 전체 구성 실패는 PRE-OP 유지 및 Master의 명시적 수정·복원 절차를 따른다.
- 다축 환경에서 한 Slave의 매핑 변경이 다른 Slave의 데이터 해석에 영향을 주지 않도록 한다.

현재 Simulator 장치 구성은 독립 .env 방식이다. 동적 PDO는 Master의 SDO 설정 경로이며, 이 RF만으로 .env에 PDO 설정 항목을 추가하거나 기존 Motion Server API를 변경하지 않는다. 재시작 시 마지막 저장 확정 매핑을 복원하며 .env 초기 매핑 설정은 추가하지 않는다. 저장 이력이 없으면 매핑 미설정 PRE-OP에서 Master 설정을 기다린다.

## TD-001과의 경계

TD-001은 기존 SDO Abort 응답 형식과 PySOEM 호환성을 다룬다. 이 RF는 잘못된 매핑을 검출하고 적절한 Abort를 생성·전달하는 동작을 추가한다. TD-001만 해결해도 현재 실패 종료 경로가 자동으로 정상 Abort로 바뀌는 것은 아니다.

오류 응답 완료 검증에는 TD-001 해결 또는 동등한 검증된 오류 응답 경로가 필요하다. PacketError를 정상 Abort로 간주하는 Master 우회는 사용하지 않는다. 구현은 기존 SDO factory 래퍼와 PDO::configureMapping 링커 래퍼를 사용한다. KickCAT 서브모듈은 수정하지 않는다.

- 복구 가능한 설정 오류는 올바른 설정·필요한 상태 전환 성공으로 원인이 해소된 것으로 처리한다. 오류 요청 이력과 현재 활성 진단은 구분한다.
- SDO 매핑 쓰기 성공은 후보 값 반영 성공이다. 전체 저장·활성화 완료는 SAFE-OP 전환 성공으로 확인한다.
- 저장 실패는 위 저장 확정 경계에 따라 기존/새 저장본을 구분한다. 저장 완료 여부가 불명확한 I/O 오류를 임의로 이전 저장본 보존으로 판정하지 않는다.
- 정확한 SDO Abort/AL 상태 코드, 공통 Diagnostic 코드·level·source·해소 조건은 이 표와 기존 RF-018 구조에 맞춰 구현 전 대조한다. 아직 수치 코드를 확정하거나 구현한 것은 아니다.
