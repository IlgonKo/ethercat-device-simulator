# RF-011 — 2축/4축 프레임 및 IPC 시간 계측 (2026-09-22)

## 목적과 조건

사용자는 가상축 4개에서 BUS_PROCESS_DATA_INCOMPLETE 이후 BUS_CONNECTION_LOST를 경험했고, 2개에서는 안정적으로 동작한다고 보고했다. 축 수에 따른 Simulator 처리 시간과 IPC 왕복 시간을 비교한다. IPC 묶음 처리 최적화는 적용하지 않는다.

- 기존 물리 축 1개 + CPX IO 1개를 유지하고 가상축만 2/4개로 전환한다.
- 동일 Windows Motion Server 소스와 Linux 계측 바이너리, 주기 8 ms, DC 비활성, sync_mode=2.
- 테스트용 포트 15100에서 상태 조회와 heartbeat ACK만 보낸다. 이동 명령·제어권 획득·저장 명령은 보내지 않는다. Motion Server의 기존 시작 초기화/Enable 절차는 실행된다.
- 두 구성 모두 모델은 현재 PP/정지 상태이며 실제 이동 중 성능 시험은 아니다. 실행 중 사용자 서비스는 먼저 종료한 상태에서 수행한다.
- 사용자 .env와 Linux에서 2축으로 수정한 config/four-axes.json은 덮어쓰지 않는다. config/timing-2-axes.json 및 timing-4-axes.json을 사용한다. 저장 공간은 기존 axis-0~3을 사용하며 명시적 저장 요청은 하지 않는다.
- 최초 준비/설정 구간의 영향을 줄이기 위해 Simulator 집계에서 시작 후 첫 10초와 이에 걸친 집계 창을 제외한다.

## 계측 정의

| 이름 | 측정 범위 |
| --- | --- |
| rx_to_reply | Linux socket read 반환 후 응답 write 반환까지. NIC/커널 수신 대기 및 실제 선로 전송 시간은 제외 |
| pdo_post_reply | PDO를 받은 축이 하나 이상인 프레임에서 응답 write 반환 후 모든 Slave routine·모델 처리 완료까지 |
| pdo_frame_busy | 같은 프레임의 수신 read 반환부터 모델 처리 완료까지 |
| ipc_axis_N_cycle | C++의 해당 축 cycle 요청 직전부터 JSON 응답 해석 완료까지. Python 계산+직렬화+소켓 왕복+스케줄링 포함 |
| ipc_all | cycle/idle/read/write 전체 요청별 왕복. 프레임당 합계가 아님 |
| slave_routine | 축별 KickCAT routine 소요 시간. SDO 콜백 IPC가 있으면 포함되므로 IPC 시간과 단순 합산하지 않음 |
| rx_gap | EtherCAT 프레임을 userspace에서 읽은 시점 사이의 간격. 선로의 송신 간격과 같다고 가정하지 않음 |
| socket_read_wait | read 호출 시간. 프레임이 오지 않는 정상 대기/타임아웃도 포함 |
| timing_log | 직전 집계 JSON 출력 비용. frame_busy에는 포함되지 않지만 다음 수신을 늦출 수 있음 |

1초마다 표본 수·최소·가중 평균 산출용 평균·최대·2 ms/8 ms 초과 횟수를 출력한다. 2 ms/8 ms 초과는 비교용 지표이지 직접적인 Master timeout 판정은 아니다. 평균 합산 시 표본 수로 가중한다. Master의 WKC는 약 1초 간격 표본이므로 모든 PDO 주기의 성공을 증명하지 않는다. 진단 상태는 별도로 보존한다.

## 실행 도구

계측은 cmmt-session.py의 --timing으로 활성화하며 로그는 build/diagnostics/<run-id>/simulator.log다. 별도 빌드 build/timing/cmmt_simulator를 사용한다. 기존 build/rf011 실행 파일은 유지한다.

```bash
python3 scripts/linux/cmmt-session.py --run-id timing2manual \
  --model-root build/model-source-da0b0a3 --config config/timing-2-axes.json \
  --binary build/timing/cmmt_simulator --timing
python3 scripts/linux/summarize-timing.py build/diagnostics/timing2manual/simulator.log --skip-seconds 10
```

4축은 config/timing-4-axes.json과 별도 run-id를 사용하고 Master 버스 구성도 해당 수량에 맞춰 재시작한다. 2축/4축 로그를 합쳐 집계하지 않는다.

Simulator 수치는 준비 구간 10초를 제외한 집계이며 Master 표본/주기 로그와 집계 경계가 정확히 같지는 않다. 4축 WKC 정상 표본 120개와 Fault 발생은 모순이 아니다. 1초 간격 조회 사이의 연속 주기 실패를 Master 진단이 탐지했다. 피드백 표본은 2축 2,145개, 4축 2,144개이고 표본의 invalid 표시는 모두 0이었다.

4축 진단의 최초 occurred_at은 18:53:58.480391 KST이며, 표본에서 관측한 resolved_at 변경은 18:53:58.480863, 18:54:24.217356, 18:55:02.011327이다. 같은 latched 진단 ID를 재사용하므로 이를 새로운 진단 ID 세 개로 세지 않는다. 마지막에는 원인이 resolve됐지만 acknowledge하지 않아 runtime_state=fault로 남았다.

### 해석과 한계

- 축 수 증가에 따라 응답 후 순차 모델 처리 부담이 늘었고, 4축에서 다음 8 ms 주기를 넘는 처리와 실제 WKC Fault를 재현했다. 순차 모델 처리 경로가 중요 병목 후보라는 근거를 확보했다.
- IPC 측정에는 Python 모델 계산과 직렬화·소켓·OS 스케줄링이 모두 포함된다. 1.346 ms 전체를 Unix socket 자체의 비용이라고 해석하지 않는다. 묶음 IPC가 이 비용을 전부 제거한다고 가정하지 않는다.
- 최초 Fault를 포함하는 18:53:58.960 종료 집계 창의 PDO 처리 최대는 6.365 ms로 8 ms 미만이지만, userspace 수신 간격은 16.823 ms였다. 모든 Fault를 단일 모델 처리 초과로 설명할 수 없다. Windows 송신/스케줄링과 Linux 수신 대기 영향도 남아 있다.
- NIC 도착 시점부터 실제 송신 완료까지의 wire latency를 측정한 것이 아니다. read 이전에 커널 큐에 쌓인 지연은 rx_to_reply에 포함되지 않는다. 프레임별 Master/Simulator 추적 ID를 맞추지 않았으므로 집계 창의 최대값들을 동일 프레임으로 간주하지 않는다.
- 이번 2분 정지 상태 시험에서 연결 상실은 재현하지 못했다. 장시간·이동 중·Axis Panel SDO 조회 부하 시험 결과로 확장하지 않는다.
- 다음 개선 검증에서는 Python 내부 계산/직렬화와 순수 대기 비용을 더 구분하거나, 묶음 IPC를 적용한 동일 조건의 전후 측정을 수행한다. 이번 작업에서 최적화나 Master timeout 완화는 하지 않았다.
