- 현재 상태: **완료**
- 상태 상세: 2026-11-26 1~4단계 구현·자동 회귀 및 5단계 물리 통합·저장/재시작·Host 장애/복구 검증 통과. 원래 혼합 구성에 새 이미지 적용, WKC 24/24·전체 정지/Disable·조작권 반환. 합의 범위 완료.
- 등록일: 2026-11-26
- 연계: [RF-015](RF-015-axis-model-semantics.md), [RF-016](RF-016-cia402-profile-adapter.md), [RF-017](RF-017-copley-fmu.md), [RF-018](RF-018-diagnostic-fault.md)

## 목적과 합의한 책임 경계

기존 F-KR CMMT 동작 모델을 FMU로 제공하여 Soft ESC 밖에서도 재사용하고, Soft ESC에서는 Copley와 같이 FMI 실행기를 통해 호출한다. 위치 계산뿐 아니라 드라이브 운전 상태·명령 처리·움직임 계산·장치 제한·Fault 동작을 포함한다. 실제 CMMT 전체 사양이나 물리적 정확도를 보증하는 의미가 아니다.

| 구성 | 책임 |
| --- | --- |
| EtherCAT Slave | EtherCAT·Mailbox·SDO/PDO 통신, 기존 Slave 측 매핑 처리 |
| CiA402 Drive 공통 계층 | 장치 OD 정의·값 저장소 소유 및 공통 접근 제공 |
| F-KR CMMT 어댑터 | 공통 장치 OD의 값을 FMU 입력으로 변환하고 FMU 출력을 같은 OD에 반영. 모델별 지원 조건·단위 변환 처리 |
| F-KR CMMT FMU | 드라이브 운전 상태, 합의한 PP/PV/Jog/Homing 동작, 위치·속도 계산, 장치 제한·Fault |
| 기존 Soft ESC 저장소 | 파라미터 파일 저장·복원. FMU에 저장 경로나 EtherCAT 매핑을 넘기지 않음 |
| 기능 모델 프로세스·FMI 실행기 | 생성·초기화·시간 진행·종료, 기존 장애 격리와 연결 |

EtherCAT Slave와 기능 모델 프로세스의 분리는 유지한다. FMU는 기능 모델 프로세스에서 라이브러리로 호출하며 FMU 전용 IPC 프로세스를 추가하지 않는다. 외부 OD와 FMU 내부 계산 상태는 구분하고 동일 장치에 두 개의 독립적인 공개 OD를 만들지 않는다.

RF-014 합의대로 장치 OD는 CiA402 Drive 공통 계층 소유다. “어댑터의 OD 관리”는 소유/생성 책임을 뜻하지 않는다. 어댑터는 기존 OD를 읽고 변환하며 계산 결과를 같은 OD에 반영한다. FMU에는 OD 주소·객체 저장소·PDO 매핑을 전달하지 않는다. FMU의 현재 위치·수락한 PP 프로파일 등 계산 상태는 두 번째 공개 OD가 아니다.

이전 Python 동작 모델은 같은 OD 인스턴스와 어댑터 단위 변환 함수를 참조했다. RF-022 구현에서는 이를 명시적 FMI 변수·호출 계약으로 대체했다. 기준 Python 모델은 tests/reference에 보존하며 제품 실행에서 선택하지 않는다.

## 확정한 제작 방식 — 2026-11-26

| 항목 | 합의 |
| --- | --- |
| 인터페이스 | FMI 3.0 Co-Simulation. 기존 공통 Fmi3Runner에 연결 |
| 구현 언어 | C++로 현재 F-KR CMMT 동작 모델 이식 |
| 빌드/산출물 | 기존 Docker Builder에서 직선용·회전용 Linux FMU 2개 생성. 공통 C++ 동작 코드 사용, 재현 가능한 소스·빌드 절차·해시 제공 |
| Python 모델 | 전환 동등성 시험의 기준 모델로 유지 |
| 동작 기준 | RF-015에서 구현·검증한 정책 유지. FMU 전환 자체를 이유로 동작 변경하지 않음 |
| 런타임 경계 | 기능 모델 프로세스에서 FMU를 라이브러리로 호출. 별도 FMU IPC 프로세스 추가 없음 |

C++ FMU에 Python 인터프리터를 포함하지 않는 구성을 목표로 한다. 언어 이식에서 생기는 수치·상태·명령 처리 차이는 동일 입력 시퀀스의 비교 시험으로 검출한다. Modelica 재작성은 이번 제작 방식이 아니다.

기존 동작을 유지하는 C++ 이식·FMU 빌드·어댑터 연결과 단계 1~4 자동 시험을 완료했다. 5단계에서 새 이미지를 운영 구성에 적용하고 물리 통합 검증을 완료했다. 제품 동작 변경이 필요한 충돌은 별도 논의한다.

## 직선·회전 FMU 선택 — 2026-11-26 확정

단일 FMU의 초기 설정으로 물리 차원을 전환하는 방안 대신 **직선용 FMU와 회전용 FMU 두 개**를 제공한다. 현재 운동학적 응답 로직은 공통 C++ 코드로 유지하고 각 FMU의 변수 단위를 고정한다. 두 산출물이 서로 다른 물리 모델 구현 완료를 뜻하지 않는다.

Soft ESC는 기존 환경설정의 축별 모델 종류와 mode 조합으로 산출물을 선택한다.

| DEVICE_SIMULATOR_AXIS_MODELS 값 | DEVICE_SIMULATOR_AXIS_MODES 값 | 선택 |
| --- | --- | --- |
| f_kr_cmmt | linear | 직선용 F-KR CMMT FMU |
| f_kr_cmmt | rotary | 회전용 F-KR CMMT FMU |
| copley_drive_sim | 기존 지원 mode | 기존 Copley 선택·지원 조건 유지 |

- 기존 f_kr_cmmt 식별자를 유지한다. 사용자에게 직선/회전별 새로운 모델 이름이나 FMU 선택용 환경변수를 요구하지 않는다.
- 동일 축 인덱스의 MODELS/MODES를 결합하여 인스턴스 생성 시 선택한다. 런타임 Controlword/Mode of Operation과 이 직선/회전 설정은 별개다.
- 직선 FMU는 m·m/s·m/s², 회전 FMU는 rad·rad/s·rad/s², 시간은 모두 s다. 변수 이름·자료형·명령/상태 계약은 공통으로 유지한다.
- 공통 OD와 사용자 측 기존 원시값·단위 설정은 유지한다. 회전축 degree↔rad 변환은 어댑터 경계에서 수행한다.
- 지원하지 않는 조합이나 필요한 산출물 누락은 구성/초기화 오류로 처리한다. 다른 모델이나 직선용 FMU로 임의 대체하지 않는다.
- FMU 파일명·내부 modelIdentifier는 구현 상세에서 정하되 두 산출물과 선언 단위를 명확히 식별한다.
- 기존 축 ID·파라미터 저장소 연결은 유지한다. 이 선택 계약만으로 저장 파일의 식별자나 스키마를 변경하지 않는다.
- 회전축 누적 위치 동작을 유지하고 modulo·최단 경로 기능은 추가하지 않는다.
- 향후 힘/토크·관성·기구 전달을 포함하는 물리 모델은 별도 동작 모델 확장으로 다룬다. 현재 공통 코드 구조를 모든 미래 물리 모델의 의무 구조로 삼지 않는다.

## RF-015와의 분담 및 진행 순서

RF-015는 동작의 의미와 합격 기준을, RF-022는 FMU 경계·산출물·실행 연결·전환 동등성을 담당한다. 두 RF의 완료를 서로 선행 조건으로 요구하지 않는다.

RF-015 1~5단계가 구현·검증된 현재 기준으로 최초의 FMU 우선 전환 제안을 갱신한다. 비교 기준은 RF-015 커밋 88d7f40이다. 이후 기준 모델에 변경이 생기면 비교 기준과 의도한 차이를 명시한다.

구체적인 실행 순서는 아래 “구현 계획”을 따른다.

동작 기준 없이 의미 변경과 FMU 이식을 동시에 수행하지 않는다. 현재 RF-015의 Copley B8/Halt 차이 등은 이식에 따라 자동 해결되는 것으로 취급하지 않는다.

## 확정한 FMU 입력·출력 계약 — 2026-11-26

명령 비트는 그대로 전달하고 위치·속도 등의 수치는 어댑터가 물리 단위로 변환한다. 아래 단위 열은 직선축 / 회전축 순서다. 두 FMU는 변수 이름·자료형을 공유하고 각 산출물에 해당 단위를 고정한다.

### 입력 — 어댑터에서 FMU로

| 변수 | FMI 형식 / 단위(직선·회전) | 의미 |
| --- | --- | --- |
| control_word | UInt16 | Enable·PP 시작·Halt·Quick Stop·Fault Reset 등 |
| mode_request | Int8 | 요청 운전 모드 |
| target_position | Float64 / m · rad | PP/CSP 목표 위치 |
| target_velocity | Float64 / m/s · rad/s | PV 목표 속도 |
| profile_velocity | Float64 / m/s · rad/s | PP 속도 및 기존 Jog 속도 계산 기준 |
| profile_acceleration | Float64 / m/s² · rad/s² | 운전 가속 |
| profile_deceleration | Float64 / m/s² · rad/s² | 운전 감속 |
| quick_stop_deceleration | Float64 / m/s² · rad/s² | Quick Stop 감속 |
| quick_stop_option | Int16 | 현재 지원값 2 |
| position_min, position_max | 각 Float64 / m · rad | 소프트웨어 위치 한계 |
| positive_velocity_limit, negative_velocity_limit | 각 Float64 / m/s · rad/s | 방향별 최대 속도 크기. 음의 방향도 크기는 비음수로 전달 |
| position_window | Float64 / m · rad | 위치 완료 허용 범위 |
| position_window_time | Float64 / s | 위치 완료 유지 시간 |

어댑터는 PDO 매핑 여부와 관계없이 같은 공통 OD의 현재 값을 읽는다. 운전 중 변경 가능한 설정도 FMU 입력으로 전달한다. 현재 운전에 반영할 시점은 RF-015 정책에 따라 FMU가 처리한다. PP 수락 시 확보한 목표·속도·가감속·한계를 입력 갱신으로 덮어쓰지 않는다. 설정값 readback과 실행 스냅샷을 구분한다.

### 출력 — FMU에서 어댑터로

| 변수 | FMI 형식 / 단위(직선·회전) | 의미 |
| --- | --- | --- |
| status_word | UInt16 | 드라이브 상태·Moving·완료·제한·참조 완료 |
| mode_display | Int8 | 실제 적용 모드 |
| actual_position | Float64 / m · rad | 현재 위치 |
| actual_velocity | Float64 / m/s · rad/s | 현재 속도 |

어댑터가 출력을 공통 OD에 반영한다. Moving·Referenced·Target reached를 별도 출력으로 중복 노출하지 않고 현재 Statusword 계약을 유지한다. 실제 적용 모드와 요청 모드가 운전 중 일시적으로 다른 것은 허용한다.

### 공통 원칙

- 별도 Stop·Fault Reset·Homing 명령 입력을 추가하지 않는다. Controlword·Mode 조합을 사용한다.
- 시뮬레이션 시간과 계산 간격은 FMI doStep 호출 인자로 전달한다. 별도 dt 입력은 만들지 않는다.
- 저장 경로·OD 주소·PDO 매핑 정보·CMMT 변환 지수는 FMU에 전달하지 않는다.
- 장치 OD의 저장/복원과 FMU 계산 상태의 재생성은 별개다.
- 변수별 갱신 규칙·초기값·CSP의 기존 계산 상수 및 회전 단위 변환은 현행 동작을 보존하도록 구현하고 비교 시험으로 검증한다.
- 비활성화·재생성·Fault는 아래 기존 정책 유지 기준을 적용한다. 자동 복구나 새로운 FMU 명령 입력은 추가하지 않는다.

## 실행 장애 복구 범위 — 2026-11-26 확정

| 대상 | 현재 복구 방식 | 장기 방향 |
| --- | --- | --- |
| FMI 호출 실패·비정상 출력 | 실행 장애를 유지하고 수동 Docker 재시작으로 복구 | 외부 요청을 통한 모델 재초기화 지원 |
| 모델 프로세스 종료·응답 시간 초과 | 해당 Host 장애를 유지하고 수동 Docker 재시작으로 복구 | 외부 요청을 통한 모델 실행부 복구·재초기화 지원 |

외부 요청 기반 재초기화는 장기 요구이며 이번 RF-022 구현 범위에는 포함하지 않는다. 현재는 자동 재생성·자동 재연결을 추가하지 않고 RF-018의 Slave 유지 및 장애 처리 정책을 따른다. 이 두 장애는 축 Fault Reset으로 해제하지 않는다.

여기서 외부 초기화는 관리 동작을 뜻한다. 현재 합의한 FMU 입력 목록에 reset 변수를 추가하거나 Controlword Fault Reset의 의미를 확대하는 결정이 아니다. 종료되거나 응답하지 않는 프로세스까지 복구할 수 있는 요청 경로, 대상 범위, 완료 판정 및 재동기화는 후속 설계에서 정한다. 외부 초기화 지원이 자동 Enable이나 이전 운전 재개를 뜻하지 않는다.

## 운전 비활성화·재생성·Fault — 기존 정책 유지

RF-014/015/018의 외부 동작을 유지하는 FMU 연결 방식을 적용한다.

### 운전 비활성화

- 어댑터가 FMU에 Controlword 0을 전달하여 비활성화를 처리한 후 계산을 일시 중단한다. 내부 속성 직접 조작이나 별도 비활성화 입력은 사용하지 않는다.
- 현재 위치와 이미 완료된 원점 참조를 보존하고 속도를 0으로 만든다. 진행 중 이동·Homing·시작 요청은 취소한다. 취소된 Homing을 완료로 처리하지 않는다.
- 공통 OD의 목표·프로파일·파라미터 설정은 보존한다. FMU의 실행 취소와 OD 설정 삭제를 혼동하지 않는다.
- 재활성화만으로 운전을 재개하지 않는다. Enable 절차와 새 명령이 필요하며 PP는 시작 비트 0 확인 후 새 상승 에지, PV/Jog는 중립 입력 후 새 운전 요청을 요구한다.
- 비활성화 처리 주기의 시간 진행과 상태 반영 순서는 기존 Python 기준 시퀀스와 비교한다. 유효한 step으로 비활성화를 완료하고 정지 시간을 몰아서 계산하지 않는다.

### 재생성

- FMU를 새로 생성하면 위치 0·속도 0·Switch On Disabled·원점 미완료로 시작한다. 이전 명령/실행 프로파일은 복원하지 않는다.
- 마지막 저장 파라미터는 기존 저장소→공통 OD→어댑터→FMU 순서로 복원한다. FMU에 파일 읽기나 PDO 매핑 복원 책임을 추가하지 않는다.
- 마스터 초기화 중 송신되는 Enable은 모델의 초기 상태와 별개다. 모델 재생성 자체가 자동 운전 재개를 의미하지 않는다.

### Fault와 Reset

| 상황 | 상태/응답 | 복구 |
| --- | --- | --- |
| 잘못된 일반 SDO 요청 | 기존 SDO Abort, 축 Fault로 승격하지 않음 | 유효한 요청 |
| 잘못된 주기 명령에 의한 어댑터 Fault | 해당 축 운전 차단·기존 Fault 투영 | 원인 수정 후 축 Fault Reset |
| 계산 가능한 FMU 드라이브 Fault | FMU Fault 유지, 비운동 명령으로 Reset 처리 | 원인 해소 후 Controlword Fault Reset |
| FMI 호출 실패·비정상 출력 | 해당 축 실행 장애 유지 | 현재 수동 Docker 재시작 |
| 모델 프로세스 종료·timeout | 해당 Host의 기존 장애 범위·Slave 유지 정책 | 현재 수동 Docker 재시작 |

축 Fault Reset은 FMU 재생성이 아니다. 위치와 완료된 원점 참조를 보존하고 성공 후 별도 Enable·새 명령을 요구한다. RF-018의 PP 복구 경로를 유지하며 미지원 복구 모드를 확장하지 않는다. FMU 내부 Fault와 어댑터/Host Fault의 검출·유효성·복구 책임을 섞지 않는다. 위치 한계 등 RF-015에서 Warning으로 정한 상황은 그대로 유지한다. 장기 관리 인터페이스 복구는 앞 절과 같이 이번 범위에서 제외한다.

## 시간 진행과 전환 동등성 — 2026-11-26 합의

별도의 사용자 정책 선택이 아니라 기존 동작을 유지하기 위한 구현·검증 기준으로 처리한다.

- 현재 Python 모델에 전달하는 계산 간격을 FMU doStep에도 동일하게 전달한다. 전환을 이유로 고정 8ms나 다른 내부 적분 주기를 새로 도입하지 않는다.
- 기존 초기 step·허용 시간 간격·PDO gap/Host timeout 처리를 대조하고 유지한다. 비활성화 기간을 재개 후 큰 step으로 계산하지 않는다.
- 비교 시험은 같은 입력값과 같은 dt 시퀀스로 진행한다. 실제 시간에 의존하는 두 독립 실행을 그대로 비교하지 않는다.
- Statusword 비트·명령 수락/무시·모드 전환·완료/취소 등 논리 상태와 전환 주기는 일치해야 한다. 수치 허용오차로 상태 차이를 숨기지 않는다.
- 위치/속도는 OD 원시값으로 환산한 해상도를 기준으로 비교한다. 양자화 전 수치 차이와 양자화 후 원시값 차이를 함께 기록한다. 허용 범위는 시험 전에 고정하며 실패 결과에 맞춰 임의 확대하지 않는다.
- 회전축은 기준 Python의 degree 값과 FMU rad 값을 같은 단위로 변환하여 비교한다. 누적 위치·경계·양/음 방향 및 장시간 누적 오차를 포함한다.
- CSP/회전의 기존 지원 범위를 유지하고 새 기능이나 물리 정확도를 추가했다고 간주하지 않는다. 기준 모델의 알려진 동작 차이가 발견되면 의도한 변경인지 이식 오류인지 구분한다.

## 2026-11-26 — RF-015 단위 계약 연결

[RF-015](RF-015-axis-model-semantics.md)의 단위 변환 합의를 적용한다. EtherCAT OD의 원시값/단위 설정은 유지하고 F-KR 어댑터에서 변환한다. 직선 FMU는 위치 m·속도 m/s·가감속 m/s², 회전 FMU는 rad·rad/s·rad/s², 공통 시간 s를 사용하며 Controlword/Statusword/Mode는 정수·비트로 유지한다. FMU가 OD 주소나 CMMT 전용 변환 지수를 직접 읽지 않고 추가 counts_per_unit 설정을 만들지 않는다. 구체 변수 계약과 기존 기능 보존은 구현 설계에서 대조한다.

## 2026-11-26 — 구현·검증 기록

[1~4단계 검증 보고서](../Validation/RF-022/stage1-4-20261126.md)를 따른다.

- 직선 `FKrCmmtLinear-linux.fmu`, 회전 `FKrCmmtRotary-linux.fmu`. 파일은 model_artifacts 아래 생성되며 Docker에는 /model_artifacts로 포함한다.
- 기존 f_kr_cmmt / linear·rotary 설정으로 자동 선택한다. 공통 OD·저장 schema 3·23개 항목·축 이름·PDO/IPC 계약 유지. 모델 내부 속성 직접 접근과 자동 Python fallback 없음.
- PP/Homing/CSP의 장치 OD readback 효과는 어댑터가 공개 입력·출력에 근거하여 반영한다. 단일 step에서 재Homing이 완료되는 경우도 포함한다.
- 비활성화는 Controlword 0과 유효한 1 ms step으로 완료한 뒤 계산을 멈춘다. 이는 Disable 처리용이며 운전 계산 dt는 기존 실행부 값이다. 이전 시간 누적 계산이나 FMU 재생성을 하지 않는다.
- 기존 Python 모델과의 동일 입력·dt 비교에서 상태·모드는 매 tick 일치, 위치/속도 정수 전송값 차이 0. 미세한 회전 부동소수점 차이는 보고서에 기록한다.
- 5단계는 새 이미지 운영 적용, 실제 Motion Server·혼합 EtherCAT·직선/회전·다축 처리 시간 및 복구 확인이다. 오프라인 통과를 물리 시험 완료로 간주하지 않는다.
